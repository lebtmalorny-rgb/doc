# Настройка Nova и ограничение эвакуации Masakari по capacity

OpenStack 2025.1 · Рекомендации по локальным архивам · 9 октября 2026

**Рекомендация:** автоматизировать расчёт резервов в Kolla-Ansible по данным каждого compute и заданной политике, а в Masakari — расчёт допустимости каждой эвакуации. Оператор задаёт политику и профиль нагрузки; абсолютные резервы и CPU-маски вычисляет автоматизация. Эвакуацию разрешать только при достаточной ёмкости Placement **и** прогнозируемой общей загрузке CPU/RAM не выше 85%. При превышении лимита или недостаточных данных запрос не отправлять.

В исследовании **60%** — рабочий предел до отказа, **85%** — предел после восстановления, оба от всего хоста, включая ОС и службы. Это не `allocation_ratio`: коэффициент `1.0` означает отсутствие переподписки, а не ограничение загрузки. Настройка Nova сама по себе не поддерживает фактическую загрузку ниже 60%/85%. Исследование capacity[^capacity-source-1], [Nova о коэффициентах](https://docs.openstack.org/nova/2025.1/admin/scheduling.html#allocation-ratios).

## Когда выполняется расчёт и задаются значения

**Оба расчёта должны выполняться автоматически:** Ansible рассчитывает конфигурацию ресурсов при подготовке деплоя, Masakari пересчитывает допустимость размещения перед переносом каждой ВМ.

| Этап | Что рассчитывается или задаётся | Где используется |
|---|---|---|
| Настройка политики | Оператор выбирает коэффициенты, минимальные резервы, предельный профиль ВМ с учётом приёма после отказа, пороги 60%/85%, окно и допустимую давность метрик, запас восстановления. | `globals.yml`, профили групп и `host_vars`; абсолютные резервы вручную не рассчитываются. |
| Подготовка деплоя | Ansible собирает фактическую топологию CPU/NUMA/SMT и доступную RAM; автоматически рассчитывает резервы, гостевые CPU-наборы и ёмкость, проверяет выполнимость профиля. | Генерация Kolla overrides для `nova-compute.conf`. |
| Деплой или управляемый reconfigure | Расчёт выполняется повторно из актуальных входов; Kolla применяет допустимую конфигурацию, Nova публикует inventory. | Автоматическая сверка результата с Placement; для работающего хоста изменения проходят проверки совместимости с размещёнными ВМ. |
| Перед каждой эвакуацией | Masakari автоматически читает актуальные allocations, незавершённые операции, запрос ВМ и метрики; заново проверяет выбранную цель. | Запрос отправляется только при соблюдении учётной ёмкости и обоих пределов CPU/RAM; недостаток достоверных данных означает запрет. |

**Автоматический расчёт не означает непрерывное изменение CPU-масок и резервов работающего хоста.** Резерв вычисляется для максимального профиля, а не по текущему числу ВМ; свободная сейчас память не повод его уменьшать. При изменении оборудования, профиля или измерений автоматизация рассчитывает новую конфигурацию. Применение, требующее освобождения CPU или превышающее остаток ресурсов, блокируется до подготовки хоста. Проверка эвакуации использует действующий inventory и не уменьшает резерв ради очередной ВМ.

Резервы и коэффициенты Nova доступны уже сейчас. Описанные вычисление резервов по политике в Kolla-Ansible и проверка по метрикам в Masakari — предлагаемые доработки; наличие штатных параметров Nova не означает, что эти алгоритмы уже реализованы.

## Настройки при деплое

В `/etc/kolla/globals.yml` задать каталог переопределений и сбор метрик:

```yaml
node_custom_config: "/etc/kolla/config"
enable_prometheus: "yes"
enable_prometheus_node_exporter: "yes"
enable_prometheus_libvirt_exporter: "yes"
enable_prometheus_openstack_exporter: "yes"
```

В Kolla-Ansible добавить этап расчёта **до формирования конфигурации Nova**. Его результат автоматически записывать в `/etc/kolla/config/nova/<inventory_hostname>/nova-compute.conf`. Этот путь поддержан локальной ролью `nova-cell` и применяется последним при объединении конфигурации. Произвольные переменные в `globals.yml` **не сработают без задач расчёта и соответствующего шаблона**. Локальная сборка конфигурации[^capacity-source-2], [механизм Kolla overrides](https://docs.openstack.org/kolla-ansible/2025.1/admin/advanced-configuration.html#openstack-service-configuration-in-kolla).

Пример **предлагаемого нового интерфейса** политики в `globals.yml` или профиле группы; это не существующие параметры Kolla:

```yaml
capacity_policy:
  cpu_allocation_ratio: 1.0
  ram_allocation_ratio: 1.0
  min_host_cpu_fraction: 0.15
  min_host_ram_fraction: 0.15
  max_instances_per_host: 64
  max_guest_ram_gib: 192
  extra_host_ram_gib: 0
  normal_utilization_limit: 0.60
  recovery_cpu_limit: 0.85
  recovery_ram_limit: 0.85
```

Ansible должен обнаруживать CPU по идентификаторам сокета/ядра/NUMA и спискам SMT siblings, а не предполагать последовательную нумерацию; RAM брать из доступного ОС объёма с согласованием единиц Nova. Затем вычислять резерв по формулам ниже с учётом процентных минимумов, выбирать целые ядра по NUMA, проверять `G + R <= T` и достаточность гостевых пулов. При неполных данных или невыполнимом профиле останавливать подготовку конфигурации с причиной. Сохранять входы и результат расчёта; повторный запуск с теми же входами не должен менять маски.

Предельные `N_VM` и `G` нельзя достоверно вывести только из оборудования или текущего списка ВМ: это требования профиля нагрузки. Их задают политикой либо получают из явно заданного набора flavor и ограничений плотности. Предлагаемые пороги политики должны также поступать в настройки нового модуля Masakari; 60% используется для контроля штатного запаса.

Начальная политика для compute без Ceph OSD и других совмещённых ролей:

| Ресурс | Рекомендуемая настройка |
|---|---|
| CPU | Начать с `cpu_allocation_ratio = 1.0`; повышение — только после испытаний профиля нагрузки. Выделить хосту целые физические ядра со всеми SMT-потоками и исключить их из гостевых CPU-наборов. |
| RAM | `ram_allocation_ratio = 1.0`; `reserved_host_memory_mb` рассчитать по максимальному числу ВМ и обещанной гостям памяти. |
| Локальный диск | `disk_allocation_ratio = 1.0`; при использовании локального хранилища отдельно рассчитать `reserved_host_disk_mb`. Это не резерв ёмкости Ceph/Cinder. |
| Плотность ВМ | Установить допустимое число ВМ для профиля. При использовании `max_instances_per_host` включить `NumInstancesFilter`, сохранив остальные необходимые фильтры; проверить параллельные операции. |

Резерв по ФТ-98 рассчитывается следующим образом:

```text
CPU: max(4, 2 × NUMA_nodes, ceil(physical_cores / 16)) физических ядер
RAM: round_up_8(max(32, 1.25 × (16 + 0.5 × N_VM + 0.01 × G + X))) GiB
```

`N_VM` — максимальное число ВМ в профиле, `G` — суммарная обещанная им RAM в GiB, а не текущее потребление; `X` — дополнительные расходы в GiB. `ceil` округляет вверх до целого числа, `round_up_8` — до кратного 8. CPU-резерв уточняется по измеренной нагрузке хоста. Коэффициенты — исходные инженерные допущения для испытаний. Если сохраняется требование **не менее 15%**, брать максимум между ним и расчётом ФТ-98, округляя CPU до целых ядер. Формулы и ограничения[^capacity-source-3].

**Иллюстративный профиль:** 256 GiB RAM, до 64 ВМ, до 192 GiB гостевой RAM; 64 физических ядра / 128 логических CPU / два NUMA-узла. При условной нумерации ядер `0–31` и `32–63`, SMT-парах `i` и `i+64`, резервируем хосту по пять ядер каждого NUMA-узла: `0–4` и `32–36` со всеми SMT-потоками. Получается 15,625% ядер под хост и 64 GiB резерва RAM:

```text
RAM при X = 0: 1.25 × (16 + 0.5 × 64 + 0.01 × 192) = 62.4 GiB
Резерв после округления: 64 GiB = 65536 MiB
Учётная ёмкость гостей при ram_allocation_ratio = 1.0: 256 − 64 = 192 GiB
```

```ini
[DEFAULT]
cpu_allocation_ratio = 1.0
ram_allocation_ratio = 1.0
disk_allocation_ratio = 1.0
reserved_host_memory_mb = 65536

[compute]
cpu_shared_set = 5-31,37-63,69-95,101-127
```

Этот INI — пример **результата автоматического расчёта**; для другого хоста Ansible формирует маску по его NUMA/SMT-топологии. Для этого shared-профиля не задавать `reserved_host_cpus` и устаревший `vcpu_pin_set`; для pinned-ВМ нужен отдельный непересекающийся `cpu_dedicated_set`. Размещение служб/IRQ на CPU хоста проверяется отдельно. Предел 192 GiB — учётная ёмкость; дополнительная проверка 85% может остановить эвакуацию раньше. [Параметры Nova](https://docs.openstack.org/nova/2025.1/configuration/config.html#DEFAULT.reserved_host_cpus), [CPU topology](https://docs.openstack.org/nova/2025.1/admin/cpu-topologies.html).

Использовать явные `*_allocation_ratio`, если конфигурация деплоя должна постоянно задавать коэффициенты; `initial_*` служат первоначальной инициализации. После деплоя сверить итоговый `nova.conf` и фактические inventory Placement. В шаблоне Kolla `reserved_host_memory_mb = 0` находится только в ветке `nova-compute-ironic` и не является настройкой KVM compute. Шаблон[^capacity-source-4].

## Правило допуска эвакуации

Для **каждой ВМ и конкретного целевого хоста** должны одновременно выполняться проверки:

```text
allocated_r + pending_r + request_r <= (total_r - reserved_r) × allocation_ratio_r
predicted_total_cpu <= 0.85
predicted_total_ram <= 0.85
```

`r` — каждый необходимый класс ресурсов: `VCPU`/`PCPU`, `MEMORY_MB`, диск и другие ресурсы запроса. Inventory и allocations брать из Placement; `pending` — уже допущенные запросы, ещё не отражённые в allocations, без двойного учёта. Резерв повторно не вычитать: исключённые CPU уже отсутствуют в гостевом inventory. Число ВМ после восстановления также должно укладываться в испытанный профиль. Проверки NUMA, huge pages, traits, PCI и affinity остаются обязательными в Nova. [Placement API](https://docs.openstack.org/api-ref/placement/).

Прогноз общей загрузки включает текущую нагрузку целевого хоста, переносимую нагрузку ВМ, допущенные операции и запас на восстановление. CPU ВМ нормировать на мощность целевого хоста; для отказавшего узла сохранять репрезентативную историю **до отказа**. Для RAM не подменять обещанную память низким RSS гостя: проверять полный бюджет гостей и служебных расходов, включая NUMA/huge pages. Зафиксировать окно измерений, обработку пиков и допустимую давность данных; отсутствие метрик не считать нулём.

Пример: прогноз `68% + 12% + 3% = 83%` проходит проверку загрузки; `74% + 12% + 3% = 89%` запрещает эту цель, даже если Placement допускает размещение. Все слагаемые здесь выражены в процентах полного целевого хоста. Формула допустимого числа отказов из исследования пригодна для планирования пула, но не заменяет проверку отдельных ВМ.

## Предлагаемые изменения Masakari и граница Mistral

В изученном архиве Masakari уже есть глобальная блокировка и последовательная эвакуация при `powerops.enabled`; проверки capacity нет. Вызов идёт из `EvacuateInstancesTask._evacuate_and_confirm()` в `API.evacuate_instance()`. При обычном восстановлении целевой хост выбирает Nova, при reserved-host восстановлении передаётся резервный хост. TaskFlow[^capacity-source-5], клиент Nova[^capacity-source-6].

1. **Добавить модуль проверки capacity** с клиентами Placement и мониторинга. Предварительно отбирать допустимые цели; итоговую проверку всех ограничений размещения и allocation claim оставлять Nova. В настройках Masakari предусмотреть включение проверки, пороги CPU/RAM, окно и максимальную давность метрик, запас восстановления и ограничение повторных попыток. Это новые параметры, которых сейчас нет.
2. **Проверять перед каждой отправкой**, под распределённой блокировкой, до перевода `VMove` в `ONGOING` и изменения состояния ВМ. Охватить обычный и reserved-host режимы. При `powerops.enabled` использовать действующую блокировку; для защиты остальных режимов вынести координацию из этой условной ветки. При недоступности координатора эвакуацию запрещать. Однократной pre-task на весь отказ недостаточно.
3. **Передавать именно проверенный target** в `evacuate_instance()`. Если проверить один хост, а отправить `host=None`, гарантия теряется. Сохранить scheduler validation: текущая микроверсия `2.53` это позволяет; `force=True` не использовать. Отказ Nova требует новой проверки цели, без автоматического перехода на непроверенный хост. [Контракт evacuate API](https://docs.openstack.org/api-ref/compute/#evacuate-server-evacuate-action).
4. **Сохранять решение и незавершённые операции** по UUID ВМ/уведомления/цели. После подтверждения сверять фактическую цель, allocations и обновлённые метрики. Не освобождать бюджет только по тайм-ауту и не отправлять повторный запрос, пока не выяснен результат предыдущего. Учитывать задержку мониторинга после запуска ВМ.
5. **При отсутствии допустимой цели остановить подачу эвакуаций** и записать причину: ресурс, текущее значение, прогноз, лимит, время данных. Для минимального изменения использовать существующий `VMove.FAILED` с сообщением `capacity_limit_exceeded` либо `capacity_data_unavailable`; отдельное состояние ожидания потребует изменения модели/API. Повтор — после устранения причины и сверки состояния. Уже восстановленные ВМ не откатывать.

**Fencing сохраняется независимым условием безопасности:** локальная `IronicFenceTask` напрямую выключает источник через Ironic и ждёт Nova `disabled/down`. Недостаток capacity запрещает восстановление на цели, но не отменяет fencing и не разрешает автоматическое включение источника. Локальный fencing[^capacity-source-7].

Mistral в этой цепочке не вызывает Masakari evacuation: его PowerOps обслуживает плановые операции, включая live migration. Переносить туда единственную проверку нельзя. Для общего лимита плановые миграции Mistral должны использовать тот же контракт проверки и учёта незавершённых операций. Реализация Mistral[^capacity-source-8].

**Граница гарантии:** блокировка Masakari не блокирует параллельные create/resize/migrate через Nova, Watcher или CLI. Для строгого общего лимита допуска нужна интеграция проверки и согласованного резервирования бюджета в Nova для всех таких операций; повторное чтение метрик или один scheduler filter не устраняют гонку. Прогноз 85% ограничивает допуск, но не гарантирует отсутствие последующего роста нагрузки уже работающих ВМ.

## Проверка результата

После деплоя прочитать итоговую конфигурацию compute и проверить каждый соответствующий resource provider; команды требуют `osc-placement`:

```bash
openstack resource provider inventory list <RP_UUID>
openstack resource provider usage show <RP_UUID>
```

В автоматизации предусмотреть сверку резервов, коэффициентов, CPU-наборов и доступности метрик с рассчитанным профилем; приведённые команды подходят также для ручной диагностики. Расчёт Ansible проверить на разных объёмах RAM, NUMA/SMT-топологиях, недостатке ресурсов и повторном запуске без изменения входов. [Справочник команд](https://docs.openstack.org/osc-placement/latest/cli/index.html).

Для будущего патча обязательны проверки: равенство лимиту допускается, превышение любого ресурса блокируется; reserved host с недостаточной capacity отклоняется; при пропавших метриках или координаторе запрос не отправляется; два engine не расходуют один остаток capacity; после тайм-аута/перезапуска нет повторной эвакуации; фактическая цель совпадает с проверенной; Nova отклоняет несовместимую NUMA/affinity-конфигурацию. Отдельно проверить конкуренцию с Nova/Mistral и задержку метрик.

Основа: `capacity_summary-main.zip`, `masakari-pvs_1.0.0_21.09.zip`, `mistral-integration-powerops-mistral-2025.1.zip`, `kolla-ansible-pvs_1.0.0_23.09 (1).zip`. Документ содержит рекомендации; патч и применение на стенде в эту работу не входят.
