# Проверка ролевой модели PVS по архиву от 21.09.2026

Проверен документ **«Ролевая Модель PVS и матрица доступа _ v3_Vault_дополнено.docx»**, 34 страницы. Основной источник реализации — **kolla-ansible-pvs_1.0.0_21.09zip.zip**, выбранный пользователем. Архив от 14.09 использован только для сравнения изменений.

**Вывод:** документ пока нельзя считать подтверждённым описанием реализации. Основные препятствия — права группы ИБ в OpenSearch, противоречащие запретам самого документа, и незашифрованный LDAP при включении интеграции с настройками по умолчанию. Подтверждённое пользователем соответствие `vm_developer = member` реализовано назначением `member` и не противоречит приведённому ДКБ-РМ-13. Дополнительные запреты матрицы не следуют из предоставленного текста ДКБ. Базовые схемы Vault остаются актуальными, но перечень постоянных копий секретов неполон; найден дефект проверки свежести аудита в режиме Vault.

Это статическая проверка поставки и локальное воспроизведение одного дефекта. Эффективные роли, overrides, версии образов и состояние установленного кластера не проверялись. Исходные DOCX и ZIP не изменены. Нормативная интерпретация уточнена по тексту ДКБ-РМ-12–15, предоставленному пользователем после первоначальной проверки. Ранее запреты из матрицы документа были ошибочно приписаны непосредственно ДКБ; это утверждение исправлено.

## Основание требований ДКБ-РМ-12–15

Источник этой части — формулировки, приведённые пользователем в разговоре; полный нормативный документ не предоставлен.

| Требование | Что установлено приведённым текстом | Вывод для ролевой модели |
| --- | --- | --- |
| ДКБ-РМ-12 | Четыре роли: разработчик ВМ, администратор безопасности средства виртуализации, администратор средства виртуализации, администратор ВМ | Основной каталог по этому пункту должен содержать эти четыре роли. Нельзя приписывать ему требование шести или семи ролей |
| ДКБ-РМ-13 | Разработчик должен создавать ВМ и изменять их конфигурации | Сопоставление с `member` допустимо по указанным возможностям; явного запрета удаления, запуска/остановки или снимков здесь нет |
| ДКБ-РМ-14 | Администратор безопасности должен читать журнал, формировать отчёты с отбором и экспортировать данные | Эти возможности необходимо подтвердить. Утверждения «только чтение» и «любая запись запрещена» в приведённой формулировке нет; запреты действующей матрицы имеют отдельный источник |
| ДКБ-РМ-15 | Администратор средства виртуализации должен управлять учётными записями, назначениями доступа, оборудованием, квотами и жизненным циклом ВМ, включая снимок с памятью | Требуется проверить весь набор функций. Наличие операции в этом перечне само по себе не означает её исключительность для этой роли |

Формулировка «должна позволять» устанавливает обязательные возможности. Из неё одной нельзя вывести «должна позволять только перечисленное». Равным образом отсутствие запрета в этом фрагменте не является основанием выдавать произвольные дополнительные права: остальные ограничения определяются полной моделью и другими применимыми требованиями.

Права администратора ВМ в предоставленном фрагменте не раскрыты: ДКБ-РМ-12 называет роль, но её нельзя без отдельного основания свести только к root/sudo гостевой ОС. `vm_user`, `vm_auditor` и Grafana следует описывать отдельно от четырёх перечисленных ролей; их статус и допустимость в полном каталоге определяются остальными требованиями.

## Как исправить матрицу доступа

В текущем документе знак `✗` прямо расшифрован как «операция запрещена». Однако отсутствие операции в перечне возможностей роли по ДКБ само по себе не обосновывает такой запрет. Нужно различать два вопроса: что требует ДКБ и что фактически разрешает реализация.

Пример для роли PVS `vm_developer`, сопоставленной с OpenStack `member`:

| Операция | Требование к разработчику по ДКБ-РМ-13 | Стандартные проектные права `member` в Nova 2025.1 |
| --- | --- | --- |
| Создание ВМ | Обязательно разрешить | Разрешено |
| Изменение конфигурации ВМ | Обязательно разрешить | Доступны операции изменения; конкретный состав проверяется по API/policy |
| Удаление ВМ | Не определено этим пунктом | Разрешено для ВМ своего проекта |
| Запуск и остановка ВМ | Не определено этим пунктом | Разрешено для ВМ своего проекта |
| Создание образа из ВМ через `create_image` | Не определено этим пунктом | Разрешено; это само по себе не подтверждает снимок с оперативной памятью |

Последняя колонка — сопоставление с [политиками upstream Nova 2025.1](https://docs.openstack.org/nova/2025.1/configuration/policy.html), а не результат проверки установленного кластера. Версия образов и overrides могут изменить права.

Для документа можно сохранить **одну матрицу фактических прав**: `✓` — разрешено конкретной реализацией; `✗` — запрещено конкретной реализацией; `?` — пока не проверено. Для каждой операции отдельно указать пункт ДКБ, требующий её разрешения, либо иной источник обязательного запрета. Тогда у `member` удаление ВМ может иметь `✓` без нарушения приведённого ДКБ-РМ-13; ставить `✗` только потому, что удаление перечислено у администратора, неправильно.

Если нужна именно **матрица требований ДКБ**, её обозначения другие: «обязательно разрешить», «явно запрещено» и «не определено приведёнными требованиями». Последнее не означает ни разрешения, ни запрета. Оно требует решения в полной ролевой модели. В предоставленном фрагменте ДКБ-РМ-12–15 прямые запреты операций не перечислены.

Четыре роли из ДКБ-РМ-12 остаются основными колонками модели. Для администратора ВМ пока недостаточно оснований заполнить все ячейки: предоставлен только пункт, называющий эту роль. Дополнительные роли продукта и их права следует обозначить отдельно от обязательной четвёрки.

Тот же принцип применяется к роли PVS **`virtualization_admin = admin`** в OpenStack. Отдельная сущность Keystone с именем `virtualization_admin` и её implied-role связь с `admin` для такого сопоставления не требуются. ДКБ-РМ-15 задаёт обязательные возможности администратора, а его фактические дополнительные права определяются scope назначения и политиками сервисов.

| Операция или область | Требование к администратору по ДКБ-РМ-15 | Как отражать фактическое право `admin` |
| --- | --- | --- |
| Удаление, запуск/остановка и перемещение ВМ | Обязательно разрешить | `✓` при подтверждении соответствующих API и области действия назначения |
| Управление оборудованием, доступом ВМ и квотами | Обязательно разрешить | Сопоставить каждую операцию с конкретным API; одного имени роли недостаточно |
| Создание и управление учётными записями, назначение доступа | Обязательно разрешить | Проверить Keystone policy и backend; назначение `admin` не превращает LDAP backend в механизм записи пользователей AD |
| Снимок конфигурации, диска и памяти ВМ | Обязательно разрешить | Пока `?`: нужен подтверждённый механизм создания и восстановления памяти |
| Иные операции OpenStack | Этим перечнем не определены | `✓`, `✗` или `?` по эффективным политикам; отсутствие в перечне ДКБ не является запретом |
| Права OpenSearch, Grafana и вход/sudo в гостевой ОС | Из назначения Keystone `admin` не следуют | Указать отдельные назначения в соответствующих компонентах; автоматическое получение этих ролей не предполагается |

Поэтому `✗` у администратора допустим как утверждение о проверенном запрете реализации или как отдельно обоснованное нормативное ограничение. Ставить его только из-за отсутствия операции в ДКБ-РМ-15 нельзя. Для обеих ролей — разработчика и администратора — нужны одинаковые правила заполнения матрицы.

### R01 · P1 · Группа ИБ сопоставлена с `all_access`

**Документ:** с. 6–7, 12. `security_admin` читает, ищет и экспортирует события; изменение событий, удаление индексов и управление OpenSearch запрещены.

**Граница вывода:** запрет записи указан в проверяемой ролевой модели. Сам предоставленный ДКБ-РМ-14 требует возможности чтения, отчётов и экспорта, но не содержит слова «только» и прямого запрета изменения. Поэтому R01 — подтверждённое расхождение с документом и вопрос избыточных полномочий, а не доказанное нарушение запрета, якобы явно записанного в ДКБ-РМ-14.

**Архив:** `ansible/roles/opensearch/defaults/main.yml:453–468` сопоставляет `ldap_group_opensearch_admin` с `all_access`. Значение группы — `cl10-ad1-sec-admin` (`ansible/group_vars/all.yml:1995`). Условие включения находится в `ansible/roles/opensearch/vars/main.yml:6`. Отдельного определения роли с буквальным именем `security_admin` в просмотренных исходниках нет.

`all_access` предоставляет полные кластерные полномочия и запись во все индексы, поэтому такое назначение противоречит модели аудитора. Семантика подтверждена [документацией OpenSearch](https://docs.opensearch.org/latest/security/access-control/users-roles/#predefined-roles).

**Исправить:** назначать группе ИБ ограниченную роль чтения целевых индексов и необходимые права Dashboards. Администрирование OpenSearch выделить отдельно. Существующая `security_audit_readonly` может быть основой, но права отчётов и сохранённых объектов нужно согласовать отдельно. Проверить суммарные права при членстве пользователя в нескольких группах.

### R02 · P2 · При соответствии `vm_developer = member` матрица содержит дополнительные запреты

**Уточнение пользователя после проверки:** `vm_developer` и `member` совпадают. В этом отчёте `vm_developer` рассматривается как название роли PVS, реализуемой ролью Keystone `member`. Отсутствие отдельной сущности Keystone `vm_developer` не является дефектом; её создание и отдельная implied-role связь не требуются для такого сопоставления.

**Уточнение по ДКБ-РМ-13:** требуются создание ВМ и изменение конфигурации; запреты удаления, запуска/остановки и снимков в предоставленном тексте отсутствуют. Указание этих операций у администратора в ДКБ-РМ-15 не делает их автоматически исключительными. Замечание о несоответствии `member` самому ДКБ-РМ-13 снято; R02 относится к лишним утверждениям и несогласованности документа.

**Документ:** с. 6–7, 12. При этом текст утверждает создание отдельной роли с цепочкой `vm_developer → member → reader`, а матрица запрещает удаление ВМ, запуск/остановку и создание снимков. Это требует согласования описания с подтверждённым сопоставлением.

**Архив:** `ansible/roles/keystone/tasks/register.yml:62–70` назначает группе `member`, что соответствует уточнению пользователя. Конкретные дополнительные ограничения Nova из матрицы в поставке не найдены. `ansible/roles/nova/tasks/config.yml:12–29` предусматривает загрузку внешнего policy-файла из `node_custom_config`, но наличие этого механизма не подтверждает поставку таких правил.

В стандартных [политиках Nova 2025.1](https://docs.openstack.org/nova/2025.1/configuration/policy.html) `servers:delete`, `servers:start`, `servers:stop` и `servers:create_image` разрешены через `project_member_or_admin`. Наследование `member` само по себе эти полномочия не исключает. Это сопоставление с upstream: в архиве `openstack_release: "latest"`, поэтому итоговые политики образов нужно проверять отдельно.

**Исправить описание:** записать «роль PVS `vm_developer` соответствует проектной роли OpenStack `member` и позволяет создавать ВМ и изменять их конфигурацию в назначенном проекте». Убрать утверждение о создании отдельной роли `vm_developer`. В матрице отдельно показывать обязательные возможности по ДКБ и эффективные права OpenStack. Запреты удаления, запуска/остановки и снимков не выводить из ДКБ-РМ-13: для сохранения каждого нужен иной конкретный источник требования и соответствующая реализация. Исходная DOCX-матрица в рамках этого обзора не изменялась.

### R03 · P1 · Заявленный LDAPS не обеспечен значением по умолчанию

**Документ:** с. 11, 13. Описано подключение к AD через LDAPs и сервисный bind.

**Архив:** `ansible/group_vars/all.yml:1979–1983` содержит выключатель LDAP со значением `no` и URL вида `ldap://…:389`. Keystone использует этот URL напрямую (`ansible/roles/keystone/templates/keystone-ldap-domain.conf.j2:4–7`). OpenSearch и Grafana вычисляют SSL по схеме URL; StartTLS явно выключен (`ansible/roles/opensearch/defaults/main.yml:297–300`, `319–322`; `ansible/roles/grafana/templates/ldap.toml.j2:2–9`).

**Следствие:** если включить LDAP и сохранить URL по умолчанию, bind и аутентификация используют незашифрованное соединение. Это условие конфигурации, а не установленный факт о кластере.

**Исправить:** закрепить защищённый URL и доверенный CA для каждого потребителя, проверку имени сервера и отказ при незашифрованном production-профиле. В приёмке проверять TLS, а не только доступность TCP-порта.

### R04 · P2 · Scope администратора и управление AD-аккаунтами описаны неточно

**Документ:** с. 5, 7–8. `virtualization_admin` представлен отдельной ролью с наследованием `admin`, назначением на домен и проект, а также управлением учётными записями.

**Уточнение сопоставления:** `virtualization_admin` — название роли PVS, реализуемой через Keystone `admin`. Отсутствие отдельной роли `virtualization_admin` и её implied-role связи не является дефектом реализации. В тексте документа следует описывать соответствие ролей. Замечание R04 сохраняется в части заявленного scope и способа управления учётными записями.

**Архив:** `ansible/roles/keystone/tasks/assign_ldap_roles.yml:47–61` выдаёт `admin` группе на конкретный проект. `group_domain` выбирает домен, в котором ищется группа; это не domain-scoped role assignment. Проект по умолчанию — `region`, его домен — `Default` (`ansible/group_vars/all.yml:1241,1247`). Назначения на домен в архиве нет. Само имя региона или проекта не доказывает ограничение всех административных API этой областью.

Кроме того, LDAP identity backend Keystone является read-only: создание и изменение пользователей AD не реализуется обычными операциями Keystone над таким backend. См. [Keystone: интеграция с LDAP](https://docs.openstack.org/keystone/2025.1/admin/configuration.html#integrate-identity-with-ldap).

**Исправить:** явно разделить домен идентичностей, домен проекта, scope назначения и административные операции сервисов. Отдельно описать управление группами/аккаунтами AD и локальными SQL-аккаунтами Keystone. Для требования управления AD нужен внешний процесс или подтверждённая интеграция.

### R05 · P2 · Grafana Org Admin описан как Server Admin

**Документ:** с. 6, 9–10. Роль мониторинга управляет пользователями и организациями Grafana, включая глобальные административные функции.

**Архив:** `ansible/roles/grafana/templates/ldap.toml.j2:24–26` задаёт только `org_role = 'Admin'`. `grafana_admin = true` отсутствует. Это разные уровни полномочий; различие отражено в [документации LDAP Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/ldap/).

**Исправить:** описать фактически выдаваемый Org Admin; если требуется Server Admin — оформить отдельное назначение и обоснование. Локального администратора Grafana отделить от роли, получаемой через AD.

### R06 · P2 · Индексы аудита, tenant и способ входа устарели

**Документ:** с. 7, 12, 18. Указаны только `flog-*`, tenant `security-audit` и Basic Auth HAProxy для `opensearch_dashboards_password`.

**Архив:** `security_audit_readonly` читает оба шаблона — `security_audit_index_prefix-*` и `opensearch_log_index_prefix-*`, по умолчанию `security-audit-v1-*` и `flog-*` (`ansible/roles/opensearch/defaults/main.yml:407–424`). В `tenants.yml` нет определения `security-audit` (`469–472`), multitenancy выключен (`ansible/roles/opensearch/templates/opensearch_dashboards.yml.j2:13`). Параметры Basic Auth удалены из обоих HAProxy frontend-описаний (`defaults/main.yml:38–52`); при аудите вход обрабатывает Security Plugin, с LDAP при его включении. ### R07 · P2 · В схемах Vault отсутствуют постоянные копии паролей аудита

**Документ:** с. 16, 19, 24–25. Постоянные административные клиентские файлы обозначены главным образом как `clouds.yaml` и OpenRC; схемы и таблицы не учитывают новые клиентские файлы аудита на deploy-узле.

**Архив:** `ansible/post-deploy.yml:88–168` создаёт на **localhost/deploy-узле** в `node_config` три файла с открытыми значениями паролей: `audit-readonly.netrc`, `audit-ingest.netrc`, `flog-ingest.netrc`. В режиме Vault используются `plaintext_*`. Mode — `0600`, владелец и группа — UID/GID пользователя из facts; задача защищена `no_log`. Рядом создаются публичный `audit-ca.pem` и `audit-curl.conf`, ссылающийся на readonly-файл. По сравнению с 14.09 клиентские файлы перенесены с первого узла OpenSearch.

Две учётные записи имеют права записи в индексы. Поэтому граница доверия deploy-узла включает и доступ к ingest, а ограничение прав файла не делает хранение «только в памяти».

**Исправить:** добавить эти файлы в схему и реестр постоянного хранения: узел, путь, владелец, назначение, права, ротация, backup и удаление. Отдельно учесть `/etc/kolla/audit-secrets.env` на первом fluentd-узле (`ansible/roles/common/tasks/config.yml:186–196`): при обычных паролях он хранит значения, при Vault references возникает R08. При обновлении инсталляции проверить оставшиеся старые копии на OpenSearch-узле.

### R08 · P2 · Heartbeat аудита передаёт ссылку Vault как пароль

**Связь с документом:** схемы runtime на с. 24–25 и критерии контроля аудита на с. 34 должны учитывать хостовые процессы вне контейнерного resolver.

**Цепочка в архиве:** `ansible/roles/common/templates/security-audit-secrets.env.j2:5–6` помещает `security_audit_readonly_password` в `AUDIT_READONLY_PASS`. Unit `audit-ingest-heartbeat.service.j2:8–9` читает файл через `EnvironmentFile` и запускает Python на хосте. В `ansible/roles/common/files/security-audit-heartbeat.py:64–69` значение возвращается без преобразования, а строки `33–35` включают его в HTTP Basic Auth. Разрешения `$(vault://…)` в этой цепочке нет.

**Проверка:** импортирован исходный Python-модуль из архива, `urlopen` заменён локальной заглушкой. Для синтетической ссылки получен заголовок с буквальным `user:$(vault://…)`. Сеть и реальные credentials не использовались. Воспроизведение: `work/review-2026-09-21/reproduce-heartbeat-vault.py`.

**Следствие:** при передаче Vault reference проверка свежести не сможет аутентифицироваться настоящим паролем; это не доказывает остановку самой доставки событий. Дефект этой цепочки сохранился относительно 14.09.

**Исправить:** обеспечить разрешение секрета для хостового потребителя с явно заданными identity, правами и жизненным циклом. Если выбирается постоянный plaintext-файл, его необходимо включить в согласованные исключения хранения. Проверить успешный опрос, отказ аутентификации и формирование сигнала о сбое.
