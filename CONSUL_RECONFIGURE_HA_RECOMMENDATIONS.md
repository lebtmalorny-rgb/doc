# Рекомендации по устранению выключений при реконфигурации Consul

Основание: [краткий вывод исследования](CONSUL_RECONFIGURE_HA_FINDINGS.md) от 13.10.2026. Ниже описаны рекомендуемые изменения; на кластере они не применялись. Ложное срабатывание HA остаётся гипотезой конкретного инцидента до сверки с журналами.

Пути к исходникам приведены в сносках относительно корня соответствующего архива; архивы и исходный код в этот репозиторий не включены.

## 1. Подтвердить цепочку инцидента

Сопоставить для одного выключенного хоста время рестарта Consul, событие Hostmonitor, notification Masakari, fencing и операцию Ironic/BMC. Зафиксировать версии и image digest работающих контейнеров, получить исходник используемого `masakari-monitors`.

На узлах с Masakari можно выполнить следующие проверки только на чтение. Пути предполагают стандартный `node_config_directory=/etc/kolla`; при переопределении использовать фактический каталог.

```bash
sudo grep -RnE 'needs recovery|Set host .* on maintenance|Ironic confirmed power off|Fencing for host' /var/log/kolla/masakari/

sudo grep -E '^(monitoring_driver|monitoring_interval|monitoring_samples|agent_manage|agent_tenant|agent_storage|matrix_config_file)[[:space:]]*=' /etc/kolla/masakari-hostmonitor/masakari-monitors.conf

sudo cat /etc/kolla/masakari-hostmonitor/matrix.yaml

sudo grep -E '^\[powerops\]|^enabled[[:space:]]*=|^host_(auto|rh)_failure_recovery_tasks[[:space:]]*=' /etc/kolla/masakari-engine/masakari.conf
```

Последняя команда выводит `enabled` из любых секций: принадлежность значения к `[powerops]` нужно проверить отдельно. Сравнить конфигурацию на хосте с загруженной конфигурацией внутри контейнера; ещё не применённый файл не доказывает активную настройку. Отсутствие строки в текущем журнале не исключает fencing: проверить ротацию и остальные узлы Engine.

## 2. До следующей реконфигурации ввести процедуру обслуживания HA

**Основная мера — установить Masakari `on_maintenance=true` до первого изменения, способного нарушить мониторинг, и проверить установку через API.** При полной `kolla-ansible reconfigure` это должно происходить до начала всей команды, а не при позднем достижении роли Masakari.

Рекомендуемый порядок:

1. Определить весь набор защищённых compute-хостов, чьи наблюдения могут измениться при рестарте затрагиваемых Consul-кластеров. При обслуживании серверов Consul этот набор может быть шире Ansible `--limit`.
2. Сохранить исходное значение `on_maintenance` каждого хоста. Проверить отсутствие активных planned PowerOps-операций и незавершённых recovery: в том числе notifications `new`, `running` и `error`, которые могут быть обработаны повторно.
3. Установить maintenance на каждом хосте и прочитать значения обратно. Повторно проверить незавершённые recovery перед началом работ. Если хотя бы один хост не защищён или операция уже выполняется, не начинать реконфигурацию.
4. Выполнить изменения Consul с последовательным рестартом и проверками готовности, описанными ниже.
5. Убедиться в восстановлении всех ожидаемых участников каждой сети, независимости endpoint-ов и нескольких последовательных успешных наблюдениях Hostmonitor. Проверить отсутствие новых fencing/recovery за окно работ.
6. Восстановить только те maintenance-флаги, которые были изменены этой процедурой. Хосты, уже находившиеся в maintenance до работ, оставить в исходном состоянии. При ошибке или неизвестном состоянии сохранить установленный maintenance и завершить процедуру с сообщением о необходимости разбора.

Во время этого окна автоматическое восстановление затронутых хостов ограничено; длительность окна должна быть контролируемой.

Это защита от новых уведомлений: Masakari API[^source-1], строки 295–309, отклоняет notification для хоста в maintenance. **Установка maintenance не отменяет уже принятое или выполняющееся recovery.** Обновление хоста также может быть запрещено, если сегмент уже занят восстановлением: тот же файл, строки 214–224. Поэтому проверки незавершённых операций обязательны.

Остановка только одного Hostmonitor не защищает от других мониторов и уже принятых уведомлений. При полной реконфигурации контейнер монитора также может быть запущен снова. Использовать такую остановку как единственную защиту не следует.

## 3. Исправить процедуру рестарта в Kolla-Ansible

После подтверждения диагноза добавить управление обслуживанием HA в orchestration реконфигурации:

- До изменений установить и проверить maintenance для полного затрагиваемого набора хостов; прерывать запуск при неполном покрытии или незавершённом recovery.
- Перезапускать серверы каждого Consul-кластера по одному, сохраняя кворум; после каждого рестарта ждать восстановления участника, лидера и ожидаемого состава peers. Затем аналогично обрабатывать клиентов.
- Между рестартами проверять готовность средствами Consul. Состояния Docker `running` или ответа HTTP 200 недостаточно: нужны ожидаемый datacenter, membership и работоспособность серверного кворума.
- Завершать обслуживание только после стабильного восстановления наблюдений Hostmonitor. При сбое не снимать maintenance автоматически в безусловном `always`.

`kolla_serial=1` можно использовать как ограничение параллелизма, но он сам не добавляет maintenance и ожидание сходимости Consul. Перестановка роли Masakari перед Consul также сама по себе не создаёт защиту.

Точки изменения: site.yml[^source-2], Consul deploy.yml[^source-3] и handlers/main.yml[^source-4]. Это предложение к доработке, а не уже существующая функция архива.

## 4. Разделить HTTP endpoint-ы Consul-сетей

Сначала проверить фактические настройки: дефолты архива могли быть переопределены. Для нескольких агентов на одном хосте каждому нужен отдельный HTTP endpoint, который Hostmonitor связывает с соответствующей сетью.

Вариант целевой схемы, сохраняющий локальный доступ к HTTP API:

| Сеть | Consul HTTP listener | Настройка Hostmonitor |
| --- | --- | --- |
| management | `127.0.0.1:8500` | `agent_manage = 127.0.0.1:8500` |
| customer | `127.0.0.1:8501` | `agent_tenant = 127.0.0.1:8501` |
| storage | `127.0.0.1:8502` | `agent_storage = 127.0.0.1:8502` |

Порты здесь — пример; перед выбором проверить их занятость. Gossip/bind-адреса при этом остаются привязанными к соответствующим сетям.

**Текущий шаблон использует один общий `consul_http_port`; приведённая схема требует изменения шаблонов.** Нужно согласованно изменить consul.hcl.j2[^source-5], masakari-monitors.conf.j2[^source-6] и Consul check.yml[^source-7]. Проверки и потребители должны брать endpoint из общей модели сети. Один лишь `masakari_hostmonitor_consul_use_loopback=false` не исправляет HTTP listener Consul.

После изменения проверить через каждый endpoint собственный datacenter и список участников. Если реально используется только одна сеть, матрица должна содержать одну сеть, без повторения одного источника под несколькими именами.

Назначение `client_addr`, `addresses.http` и `ports` подтверждается [документацией Consul](https://developer.hashicorp.com/consul/docs/reference/agent/configuration-file/general): внутренний `bind_addr` и HTTP listener задают разные виды связи.

## 5. Устранить путаницу с samples и добавить фильтрацию кратких сбоев

Использовать имена, которые действительно читает шаблон. Пример настройки для проверки на стенде, а не гарантированно подходящие значения для любого кластера:

До — значения используемых переменных в архиве:

```yaml
masakari_hostmonitor_monitoring_interval: 60
masakari_hostmonitor_monitoring_samples: 1
```

После — пример трёх наблюдений с интервалом 30 секунд:

```yaml
masakari_hostmonitor_monitoring_interval: 30
masakari_hostmonitor_monitoring_samples: 3
```

Проверить итоговые `monitoring_interval` и `monitoring_samples` в конфигурации работающего Hostmonitor, включая пользовательские merge overrides. Неиспользуемые `masakari_consul_monitoring_*` удалить из документации/дефолтов либо оформить явную совместимость с однозначным приоритетом.

Большее число samples увеличивает время обнаружения настоящего отказа. Выбирать значения по измеренной длительности переходных состояний Consul и допустимому времени реакции HA. Интервал опроса не является гарантированным периодом непрерывного отказа. Фильтрация не заменяет maintenance при плановой реконфигурации. Семантику подтвердить по используемой сборке `masakari-monitors`; для сравнения доступен [upstream Consul manager](https://github.com/openstack/masakari-monitors/blob/stable/2025.1/masakarimonitors/hostmonitor/consul_check/manager.py).

## 6. Проверить результат до применения в рабочем кластере

На изолированном стенде проверить следующие сценарии:

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Реконфигурация без изменений | Нет лишнего рестарта Consul и физических power-операций |
| Изменение Consul с рестартом | Maintenance установлен заранее; нет fencing; Consul восстанавливается до снятия защиты |
| Отказ одного независимого источника при трёх сетях и `all_down` | Нет ложного состояния `[down, down, down]` и recovery |
| Ошибка HTTP API Consul | Поведение соответствует проверенному драйверу; ошибка запроса не превращается автоматически в отказ всех хостов |
| Ошибка рестарта или неполный состав участников | Процедура завершается ошибкой, maintenance сохраняется |
| Recovery уже выполняется до начала работ | Реконфигурация не начинается; maintenance не выдаётся за отмену fencing |
| Настоящий отказ после завершения обслуживания | HA снова обнаруживает отказ и выполняет штатное восстановление |

Сохранить временную шкалу Ansible, Consul, Hostmonitor, Masakari и Ironic, а также исходные и итоговые maintenance-флаги. Проверка шаблонов подтверждает формирование конфигурации; отсутствие ложного выключения требует отдельной проверки работающей системы.

Не устранять проблему удалением `ironic_fence` из recovery: это убирает подтверждение изоляции исходного хоста перед эвакуацией. Исправлению подлежат процедура обслуживания, независимость наблюдений и условия детектирования отказа.
