# Dorado V6 / FC: диагностика и исправление Logical unit not supported

Дата: **14.10.2026**.

Область: Linux DM Multipath, контейнерный `multipathd`, Nova/Cinder в Kolla,
предоставленный форк PVS. Это инструкция для оператора; команды на кластере
при её подготовке не выполнялись. Для UltraPath или NVMe-oF нужна другая процедура.

## 1. Что означает ошибка и с чего начать

`Logical unit not supported` — SCSI additional sense **25h/00h**: адресуемый
logical unit не поддерживается. Это не сообщение об отсутствии
`multipath.conf` и не утверждение, что OpenStack не поддерживает Dorado V6.
[Определение T10](https://www.t10.org/lists/asc-num.txt).

**Первый вопрос: должен ли этот том сейчас использоваться на этом хосте?**

| Подтверждённая ситуация | Что исправлять |
|---|---|
| Том нужен ВМ/операции Cinder, но mapping пропал или неверен | Восстановить доступ к тому же LUN; раздел 7 |
| Mapping корректен, ошибка только на части путей | Проверить конкретные инициаторы/целевые порты и адреса LUN; раздел 8 |
| Том штатно отключён, потребителей нет, на Linux остались устройства | Завершить локальную очистку только этого тома; раздел 9 |
| Ошибка повторяется после detach | Разобрать порядок локальной очистки и unmap; раздел 10 |
| Известна только ошибка, WWID или назначение тома не установлены | Выполнить диагностику ниже; команды удаления пока не применять |

Разделы 2–6 собирают состояние. Разделы 7–10 описывают изменения по выбранной
ветке. Не выполнять весь документ подряд как один скрипт.

При потере I/O у действующей ВМ сначала сохранить её состояние и установить
владельца тома. Не удалять устройства и не делать повторный detach ради проверки.
Команды `multipath -F`, `dmsetup remove -f`, массовый rescan, удаление attachments
и принудительная смена статуса Cinder не являются исправлением этой ошибки.

## 2. Зафиксировать узел, время и точную ошибку

Выполнять на Linux-хосте, в kernel log которого появилась ошибка, с правами root.
Время ниже заменить интервалом инцидента; выбрать один часовой пояс, например UTC.

```bash
hostname -f
date -u
uname -r
cat /etc/os-release

INCIDENT_START='YYYY-MM-DD HH:MM:SS UTC'
INCIDENT_END='YYYY-MM-DD HH:MM:SS UTC'
journalctl -k --utc --since "$INCIDENT_START" --until "$INCIDENT_END" \
  -o short-iso-precise --no-pager
```

Сохранить полный фрагмент: строку `sd H:C:T:L: [sdX]`, sense key, additional
sense, команду/CDB, последующий `I/O error` и сообщения удаления/добавления
устройства. Если узел перезагружался, выбрать журнал нужной загрузки через
`journalctl --list-boots` и `-b`; текущие имена устройств могли измениться.

Не связывать ошибку с REST unmap только по близости строк: нужны одинаковые
узел, том/WWID и согласованное время. В исходных материалах ошибки на `compute03`
и `ctrl01` не были доказаны как одна последовательность.

## 3. Связать sdX → SCSI-адрес → WWID → multipath-карту

`sdX` ниже заменить именем из журнала **только после проверки, что оно всё ещё
относится к тому же устройству**. Буквы `sdX` могут использоваться повторно.

```bash
SDEV='sdX'
readlink -f "/sys/class/block/$SDEV/device"
cat "/sys/class/block/$SDEV/device/wwid"
cat "/sys/class/block/$SDEV/device/state"
udevadm info --query=property --name="/dev/$SDEV"
lsblk -o NAME,TYPE,PKNAME,HCTL,WWN,SERIAL,SIZE,MOUNTPOINT
ls -l "/sys/class/block/$SDEV/holders"
```

Зафиксировать H:C:T:L, WWID и свойства `ID_WWN`/`ID_SERIAL`, если они есть.
H — номер SCSI host/HBA, C — канал, T — target, L — адрес LUN на этом пути.
**L здесь не равен автоматически внутреннему ID LUN в Dorado.**

Если sysfs-устройства уже нет или имя переиспользовано, не восстанавливать
идентичность по размеру/букве: нужны журналы подключения, сохранённая топология
или данные attachment. Отсутствие файла `wwid` в данной сборке также не означает,
что WWID не существует; сопоставить udev, multipath и данные СХД.

Сначала определить управляющий демон:

```bash
podman ps --format '{{.Names}} {{.Image}}'
pgrep -a -x multipathd
systemctl show multipathd.service multipathd.socket \
  -p Id -p ActiveState -p SubState -p MainPID -p UnitFileState
```

`pgrep` видит и контейнерные процессы. Сопоставить PID с контейнером/cgroup.
Если обнаружен другой демон или активный системный socket при контейнерной
схеме, сначала установить владельца: клиентский запрос может активировать
системный service. Не останавливать его автоматически.

После подтверждения работающего контейнерного демона:

```bash
podman exec -u 0 multipathd multipathd show paths
podman exec -u 0 multipathd multipathd show maps topology
podman exec -u 0 multipathd multipathd show maps status
dmsetup info -c -o name,uuid,open,major,minor
dmsetup ls --tree
```

Для Docker заменить `podman`; имя контейнера взять из фактического списка.
Для намеренно хостового демона команды выполняются в ОС, без запуска второго.
`show` читает состояние уже выбранного демона.

Установить имя нужной карты и её `dm-N`, затем проверить связи:

```bash
DM_NODE='dm-N'
cat "/sys/class/block/$DM_NODE/dm/name"
cat "/sys/class/block/$DM_NODE/dm/uuid"
ls -l "/sys/class/block/$DM_NODE/slaves"
ls -l "/sys/class/block/$DM_NODE/holders"
```

`slaves` — нижележащие пути; `holders` — устройства выше, например dm-crypt
или partition-карты. Наличие holder не означает ошибку: это может быть нужный
потребитель. Карта с другими рабочими путями не должна удаляться из-за одного
ошибочного пути.

## 4. Определить владельца тома в OpenStack и на Linux

На административном узле с настроенным OpenStack CLI:

```bash
VOL_UUID='UUID_ТОМА'
openstack volume show "$VOL_UUID" -f yaml \
  -c id -c status -c attachments -c multiattach -c os-vol-host-attr:host

SERVER_UUID='UUID_ВМ'
openstack server volume list "$SERVER_UUID" -f yaml
openstack server show "$SERVER_UUID" -f yaml \
  -c id -c status -c OS-EXT-SRV-ATTR:host -c OS-EXT-SRV-ATTR:instance_name
```

Команды по ВМ выполнять, если она есть у исследуемого attachment. При multiattach
проверить всех потребителей и хосты. Если поле скрыто правами или не поддержано
версией CLI, получить его разрешённым административным способом; пустой вывод
не считать подтверждением отсутствия подключения.

В работающей Nova проверить источник диска в libvirt:

```bash
DOMAIN='instance-XXXXXXXX'
podman exec nova_libvirt virsh -c qemu:///system domblklist "$DOMAIN" --details
```

Использовать существующую схему аутентификации libvirt; не менять её ради команды.
Проследить source до WWID, включая symlink и dm-crypt. Проверить также неактивную
конфигурацию домена через `domblklist --inactive`, если том может быть нужен
выключенной ВМ. Для ручной очистки должны быть исключены и другие домены.

Если ошибка на узле `cinder_volume`, проверить локальные image-transfer,
clone, backup и другие операции подключения: том может использоваться ими
без attachment к ВМ. Проверить Glance/Cinder-backup, если они подключают эти LUN.

В ОС дополнительно:

```bash
findmnt -rn -o SOURCE,TARGET,FSTYPE
swapon --show
MAP_PATH='/dev/mapper/ИМЯ_КАРТЫ'
fuser -v "$MAP_PATH" "/dev/$SDEV"
```

Отсутствие host mountpoint не означает, что том свободен: QEMU может открывать
его как блочное устройство. Пустой `fuser` и `open=0` также не заменяют проверку
attachments, QEMU, верхних DM-устройств и текущих операций Cinder.

Связь UUID Cinder и WWID брать из журналов подключения/данных драйвера и сверять
с Dorado. Не вычислять её из имени LUN или размера.

## 5. Проверить FC-инициаторы и mapping на Dorado

На затронутом Linux-хосте получить WWPN его портов и состояние FC:

```bash
for p in /sys/class/fc_host/host*; do
  [ -d "$p" ] || continue
  printf '\n%s\n' "$p"
  cat "$p/port_name" "$p/node_name" "$p/port_state"
done

for p in /sys/class/fc_transport/target*; do
  [ -d "$p" ] || continue
  printf '\n%s\n' "$p"
  cat "$p/port_name" "$p/node_name"
done
```

Для H:C:T:L сопоставить `hostH` и `targetH:C:T`: это связывает путь с локальным
инициатором и целевым FC-портом. `Online`/`Link Up` подтверждает состояние
соединения, но не предоставление нужного LUN.

В DeviceManager проверить именно эти объекты:

| Объект | Что сопоставить |
|---|---|
| LUN | WWN/идентификатор, состояние и внутренний ID |
| Host и FC Initiators | WWPN данного Linux-хоста, принадлежность нужному Host |
| Host Group, LUN Group, Mapping View | Связь нужного Host с нужным LUN |
| Host LUN ID | Адрес, под которым этот LUN предоставляется данному хосту |
| Target ports / Port Group | Порты, через которые ожидаются пути |
| Аудит операций | Кто и когда изменял mapping, LUN Group или принадлежность инициаторов |

Для Dorado 6.1.2 документирован следующий **запрос чтения** в CLI СХД:

```text
show mapping_view general
show mapping_view general mapping_view_id=<ID> detail=enable
```

Проверить синтаксис по справке установленной версии. Вывод содержит Host,
инициаторы, LUN и порты. [Справочник Huawei](https://support.huawei.cn/enterprise/en/doc/EDOC1100194663/acb24571/show-mapping_view-general).

Представления Linux WWID и Dorado WWN могут различаться служебным префиксом
и оформлением. Сопоставлять идентификатор устройства/VPD, не удалять символы
наугад. Внутренний LUN ID, Host LUN ID, WWID и UUID Cinder — разные идентификаторы.
При HyperMetro проверить оба массива и ожидаемую топологию подключения.

## 6. Собрать одну временную последовательность

Для того же UUID/WWID собрать kernel log, Nova/Cinder, multipathd и аудит Dorado.
В типовой Kolla логи находятся под `/var/log/kolla/`; уточнить реальные файлы
и ротацию. Начать с поиска UUID в относящихся к инциденту логах:

```bash
grep -n -F "$VOL_UUID" /var/log/kolla/nova/nova-compute.log
grep -n -F "$VOL_UUID" /var/log/kolla/cinder/cinder-volume.log
```

Читать соответствующие файлы на тех узлах, где выполнялись операции. По найденным
строкам выбрать request ID и полный временной фрагмент, включая строки без UUID.
Не трактовать отсутствие записи в текущем файле как отсутствие события.

| Этап | Что искать |
|---|---|
| Подключение | UUID, WWID, target WWPN/LUN, путь, возвращённый os-brick |
| Начало отключения | `disconnect_volume`, `terminate_connection`, request ID |
| Локальная очистка | flush, `map in use`, holders, `Remove SCSI device`, `leftovers may remain`, `Disconnect failed` |
| Изменение Dorado | remove LUN from group, unmap, `remove_fc_from_host`, время и инициатор операции |
| Последующая ошибка | Тот же WWID/H:C:T:L и `25/00`, затем результат I/O |

Отдельно записать: mapping исчез до локального отключения, после него или
вообще не менялся. Успешный REST-ответ не доказывает успешное удаление путей
на Linux. `remove_fc_from_host` может быть частью штатного удаления последнего
подключения; его ошибочность подтверждается оставшимися нужными томами.

## 7. Исправление A: том нужен, mapping отсутствует или неверен

1. Подтвердить UUID → WWID → LUN и всех действующих потребителей. Если соответствие
   неоднозначно, восстановление mapping не начинать.
2. Установить, кто управляет mapping: Cinder или ручная конфигурация. Исключить
   повторное автоматическое снятие mapping той же незавершённой операцией.
3. Восстановить доступ **к исходному LUN**, для нужных WWPN/Host и ожидаемого
   Host LUN ID. Не создавать новый LUN с тем же именем и не переносить инициатор
   между Host без проверки других томов. Изменение на Dorado выполняется
   процедурой для установленной версии с проверкой исходных параметров.
4. Проверить возвращение прежних путей и карты. Если нужен поиск отсутствующего
   пути, использовать точечный scan ниже. Не менять WWID действующей карты.
5. Проверить I/O в госте/приложении: восстановление пути не обязательно снимает
   паузу ВМ или ошибку файловой системы. Эти последствия устраняются отдельно.

Если это обычный дополнительный диск, приложение остановлено и штатный detach
возможен, альтернативой ручному восстановлению является согласованный цикл
отключения/подключения через Nova. Для root-диска, аварийного I/O и multiattach
это не универсальный способ восстановления.

```bash
# ИЗМЕНЕНИЕ. Только после выбора этой процедуры и подготовки приложения.
openstack server remove volume "$SERVER_UUID" "$VOL_UUID"
```

Дождаться завершения, проверить отсутствие диска у нужной ВМ и локальную очистку.
Только затем, отдельным шагом:

```bash
# ИЗМЕНЕНИЕ. После подтверждённого успешного отключения.
openstack server add volume "$SERVER_UUID" "$VOL_UUID"
```

При ошибке detach не продолжать к add и не подменять операцию удалением записи
attachment или `volume set --state available`: это не гарантирует физическое
отключение диска. [Команды OpenStack](https://docs.openstack.org/python-openstackclient/2025.1/cli/decoder.html),
[границы attachment API](https://docs.openstack.org/python-openstackclient/latest/cli/command-objects/volume/v3/index.html).

### Точечный поиск восстановленного пути

Только после восстановления правильного mapping и проверки H:C:T:L. Это
**изменение состояния Linux**, не диагностический запрос. Выполнять на хосте
от root; подставить числа из установленного соответствия, а не внутренний
LUN ID массива:

```bash
SCAN_HCTL='H:C:T:L'
if [[ "$SCAN_HCTL" =~ ^[0-9]+:[0-9]+:[0-9]+:[0-9]+$ ]]; then
  IFS=: read -r SCAN_H SCAN_C SCAN_T SCAN_L <<< "$SCAN_HCTL"
  printf '%s %s %s\n' "$SCAN_C" "$SCAN_T" "$SCAN_L" \
    > "/sys/class/scsi_host/host$SCAN_H/scan"
else
  printf '%s\n' 'Сначала укажите проверенный H:C:T:L' >&2
fi
```

Повторить только для недостающих проверенных путей этого LUN. Команда не удаляет
старые устройства и не исправляет неверный mapping. Если target/путь нельзя
однозначно определить, сначала продолжить диагностику FC. Не заменять адрес
на `- - -` и не выполнять LIP/reset HBA как автоматический следующий шаг.
[Механизм точечного добавления пути](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/7/html/storage_administration_guide/adding_storage-device-or-path).

## 8. Исправление B: часть путей работает, часть отвечает 25/00

Сохранить работающую карту и здоровые пути. Для каждого плохого пути сравнить
инициатор WWPN → target WWPN → Host LUN ID с рабочим путём и mapping на Dorado.
Исправлять найденное расхождение на соответствующем Host/порту/представлении LUN.
Если ошибка появилась после смены mapping, проверить, не остался ли старый адрес.

Если FC-порт offline, это отдельное основание проверить fabric, zoning и физику.
Сам по себе SCSI-ответ 25/00 не доказывает обрыв кабеля. Не менять ALUA, таймауты
или общий профиль Dorado вместо восстановления правильного доступа.

При HyperMetro нельзя считать все пути равноценными без знания режима массива.
После исправления проверить ожидаемые группы и приоритеты, а не только число
видимых `sdX`. Удалять действующую multipath-карту для лечения одного пути не нужно.

## 9. Исправление C: том отключён, остались старые устройства

Предпочтительно дать штатному detach завершить очистку. Ручная очистка допустима
только для установленного WWID на конкретном хосте, когда одновременно подтверждено:

- Нет действующего или ожидающего подключения к этому хосту, включая multiattach.
- Ни QEMU, ни локальная операция Cinder/Glance/backup, ни хостовая ФС/swap не
  используют том. Проверены все верхние устройства, включая dm-crypt и разделы.
- Нет незавершённых записей, которые нужно сохранить. Если I/O завис или требуется
  восстановление данных, сначала восстанавливается доступ по разделу 7.
- Зафиксированы карта, WWID, полный список её SCSI-путей и H:C:T:L. Автоматизация
  не выполняет параллельно новый attach/detach этого тома.

Очищать сверху вниз. Если карту удерживают разделы/dm-crypt/процесс, сначала
выяснить их владельца и корректно завершить его работу. `busy` нельзя обходить
силовым удалением.

Сначала выполнить только чтение для подтверждённого имени карты:

```bash
MAP_NAME='ИМЯ_ПРОВЕРЕННОЙ_КАРТЫ'
dmsetup info -c -o name,uuid,open "$MAP_NAME"
dmsetup deps -o devname "$MAP_NAME"
```

Сохранить список путей: после удаления карты её `slaves` исчезнут.
При выполненных условиях выше удалить **одну** неиспользуемую карту:

```bash
# ИЗМЕНЕНИЕ. Только для подтверждённого неиспользуемого тома.
podman exec -u 0 multipathd multipath -f "$MAP_NAME"
```

Если команда завершилась ошибкой, зависла либо карта появилась снова —
остановиться и выяснить владельца/событие. Не добавлять `-F` или `dmsetup remove -f`.
Не считать успешное удаление карты доказательством корректного detach в Cinder.
Повторить `dmsetup info` и проверку `holders` у сохранённых путей: перед следующим
шагом карта должна отсутствовать, а пути не должны иметь верхних потребителей.

Затем удалять оставшиеся SCSI-пути этого отключённого тома **по одному**.
Непосредственно перед каждым удалением заново сверить имя, H:C:T:L и WWID
с сохранёнными данными; процедура не должна захватить переиспользованный `sdX`.

```bash
# ИЗМЕНЕНИЕ. SDEV и EXPECTED_HCTL заполнить по данным текущей проверки.
# Проверка адреса ниже дополняет, но не заменяет ручную сверку WWID.
SDEV='sdX'
EXPECTED_HCTL='H:C:T:L'
if [[ "$SDEV" =~ ^sd[a-z]+$ ]] \
   && [[ "$EXPECTED_HCTL" =~ ^[0-9]+:[0-9]+:[0-9]+:[0-9]+$ ]] \
   && [ -e "/sys/class/block/$SDEV/device/delete" ] \
   && ! compgen -G "/sys/class/block/$SDEV/holders/*" > /dev/null \
   && [ "$(basename "$(readlink -f "/sys/class/block/$SDEV/device")")" = "$EXPECTED_HCTL" ]; then
  printf '1\n' > "/sys/class/block/$SDEV/device/delete"
else
  printf '%s\n' 'Устройство или адрес не подтверждены; удаление не выполнено' >&2
fi
```

Запись в `device/delete` убирает SCSI-устройство из данного Linux-хоста;
она не стирает LUN на Dorado, но обрывает обращения к этому пути. Именно поэтому
проверки потребителей обязательны. Не применять к пути активного тома по этой
процедуре. Если карты уже не было, шаг `multipath -f` пропускается, но проверки
владения для каждого оставшегося SCSI-устройства сохраняются.

Принцип удаления неиспользуемого устройства описан у
[Red Hat](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/epub/configuring_device_mapper_multipath/proc_mpathd-operation-managing-mpath).
Для данного случая не нужны `wipefs`, `pvremove`, удаление разделов на LUN
или очистка всех WWID: содержимое отключённого тома сохраняется.

## 10. Исправление D: после detach ошибка возникает повторно

Разовая очистка оставшихся устройств снимает следствие. Чтобы исправить
повторение, по разделу 6 найти первое незавершённое действие:

| Подтверждённый сбой | Направление исправления |
|---|---|
| Утилита внутри Nova/Cinder не находит конфиг | Исправить доставку через Kolla и проверить применённые файлы |
| Удаление карты блокирует реальный потребитель | Исправить порядок завершения QEMU/image-transfer/другой операции |
| После отключения остаются ненужные partition-карты | Проверить udev/kpartx и применимость `skip_kpartx` для этих LUN |
| Локальный flush/disconnect не завершился, затем снят mapping | Проверить конкретный путь os-brick и обработку ошибки вызывающим сервисом |
| После отключения одного тома потеряли доступ другие | Проверить область cleanup Huawei-драйвера, оставшиеся LUN, multiattach и совместное использование Host |

В предоставленном `os-brick-pvs.zip` FC-код вызывает
`remove_scsi_device(device_path, flush=flush)` без передачи внешнего `force`.
Это повод проверить соответствующую ветку при ошибке flush, а не рекомендация
включить принудительное удаление. Для обычного multipath индивидуальный flush
пути может не требоваться; совпадение версии не доказывает попадание в ветку.

В локальном Huawei FC-драйвере после удаления LUN из группы проверяется число
оставшихся LUN; дальнейшая очистка может включать инициаторы, Host Group
и Mapping View. Прежде чем менять код, сравнить установленный драйвер и журналы
с исходниками, особенно если объекты СХД разделяют разные backend/ручные mapping.

Доставка конфигурации описана в
[инструкции Nova/Cinder](KOLLA_MULTIPATH_NOVA_CINDER_FIX.md).
Изменения os-brick/Huawei требуют воспроизведения подтверждённой ветки и теста,
что отключение одного тома не затрагивает другой. В рамках этой инструкции
таких исправлений в код не внесено.

## 11. Проверка результата

Для восстановленного тома проверить:

1. UUID/WWID соответствуют исходному LUN; Host LUN ID и FC-пути ожидаемые.
2. Доступны нужные пути и multipath-карта; выбранный потребителем путь
   приводит к этой карте, включая dm-crypt при шифровании.
3. Приложение/ВМ выполняет I/O; проверка данных проводится средствами приложения
   или на выделенном тестовом томе. Не запускать запись `fio` по продуктивному LUN.
4. После времени исправления новые `25/00` для этого тома не появляются;
   проверяется интервал с реальной нагрузкой, а не только отсутствие новых строк.

Для штатно отключённого тома проверить отсутствие локальных путей/карты и
потребителей, ожидаемое состояние OpenStack, сохранность самого LUN и доступность
соседних томов. Не выполнять rescan отключённого тома ради «проверки очистки».

Если исправлялся detach-код или политика, на тестовых данных проверить:
подключение/отключение одного тома, отключение одного из двух при I/O второго,
отключение последнего и применимые операции image-transfer. До этих проверок
отсутствие сообщений не считать подтверждением устранения причины.
