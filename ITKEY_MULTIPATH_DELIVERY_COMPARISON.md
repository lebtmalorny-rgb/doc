# Доставка multipath.conf: ITkey и рекомендации для форка PVS

Дата проверки: **14.10.2026**.

## Схемы рендера и доставки

| Случай | Короткая схема |
|---|---|
| **ITkey: демон** | Источник → Ansible/Jinja → `/etc/kolla/multipathd/` на хосте → mount каталога → `kolla_set_configs` → `/etc/multipath.conf` в контейнере |
| **ITkey: Nova/Cinder/Glance** | Сборка образа → минимальный `defaults {}` в слое → `/etc/multipath.conf` в контейнере; Ansible-рендера нет |
| **PVS: контейнеры, рекомендация** | Общий источник → Ansible/Jinja для каждой роли → `/etc/kolla/<service>/` → mount каталога → `kolla_set_configs` → `/etc/multipath.conf` каждого контейнера |
| **PVS: ОС хоста, условная рекомендация** | Общий источник → Ansible/Jinja → сразу хостовый `/etc/multipath.conf` → локальные утилиты/udev |

Для PVS включаются только нужные потребители; Glance — при Cinder FC/iSCSI store
с multipath. `kolla_set_configs` копирует уже отрендеренный файл. У ITkey доставка
в **хостовый** `/etc/multipath.conf` в проверенных задачах не найдена.

## Основание проверки

Основа: локальные образы ITkey `ks2025.2.2` и `ks2026.2`, извлечённые роли
Kolla-Ansible и ранее подготовленные рекомендации для `kolla-ansible-pvs`.
Проверены исходники и содержимое архивов. Работающая инфраструктура не проверялась.

Пути `ansible/...` в описании ITkey относятся к каталогу
`/var/lib/kolla/venv/share/kolla-ansible/` внутри образа
`repo.itkey.com/project_k/kolla-ansible:ks2026.2`.
Клиентские образы имеют имена `repo.itkey.com/project_k/<service>:<release>-sberlinux`,
где `<service>` — `nova-compute`, `cinder-volume` или `glance-api`,
а `<release>` — `ks2025.2.2` или `ks2026.2`.
Они исследованы в архивах `keystack-ks2025.2.2-sberlinux-docker-images.tar`
и `keystack-ks2026.2-sberlinux-docker-images.tar` из локального комплекта ITkey.
Архивы и извлечённые исходники в этот документационный репозиторий не включены.

## Краткий вывод

У ITkey используются два способа доставки:

- **`multipathd`:** полноценный конфиг рендерится Ansible и устанавливается
  в контейнер через `config_files` и `kolla_set_configs`.
- **Nova/Cinder/Glance:** минимальный `/etc/multipath.conf` заранее создаётся
  при сборке образов; соответствующие роли не рендерят и не доставляют этот файл.

Рекомендация для форка PVS расширяет штатный механизм Ansible на клиентские
контейнеры: каждый получает управляемую копию конфигурации из того же источника,
который выбран для демона на данном хосте.

Минимальный файл ITkey закрывает отсутствие `/etc/multipath.conf`. Предлагаемая
схема дополнительно обеспечивает управление содержимым и его обновлениями.
Полный одинаковый файл нельзя объявлять обязательным условием любого работающего
multipath-развёртывания.

На хосте обязательны ядро/device-mapper, доступ к СХД и обработка устройств.
Хостовый `/etc/multipath.conf` нужен, если его используют локальные утилиты,
udev или загрузка ОС. Для PVS его предлагается доставлять отдельной задачей
из согласованного источника после определения этих потребителей — разделы 7–9.

## 1. Как ITkey доставляет конфиг демона

Роль `multipathd` выбирает первый существующий источник:

```text
1. {{ node_custom_config }}/multipath/{{ inventory_hostname }}/multipath.conf
2. {{ node_custom_config }}/multipath.conf
3. roles/multipathd/templates/multipath.conf.j2
```

При стандартных путях первые два источника находятся на узле развёртывания
в `/etc/kolla/config/`. В host-specific пути используется имя из inventory.

```text
Узел развёртывания:
выбранный источник
    │ Ansible template: Jinja-рендер для целевого хоста
    ▼
Целевой узел:
/etc/kolla/multipathd/multipath.conf
    │ каталог /etc/kolla/multipathd/ смонтирован в контейнер read-only
    ▼
Контейнер multipathd:
/var/lib/kolla/config_files/multipath.conf
    │ kolla_set_configs: установка по описанию в config.json
    ▼
/etc/multipath.conf
    │
    ▼
чтение демоном multipathd
```

Ansible отдельно рендерит `multipathd.json.j2` в
`/etc/kolla/multipathd/config.json`. В нём объявлены источник, назначение,
владелец и права файла. В контейнере Jinja-рендера этого конфига уже нет:
`kolla_set_configs` устанавливает подготовленный файл.

**`with_first_found` не объединяет конфиги.** Пользовательский файл целиком
заменяет штатный шаблон. Huawei-профиль из шаблона `ks2026.2` автоматически
к пользовательскому конфигу не добавляется.

Источники: задачи роли (`ansible/roles/multipathd/tasks/config.yml`),
монтирования (`ansible/roles/multipathd/defaults/main.yml`),
JSON-шаблон (`ansible/roles/multipathd/templates/multipathd.json.j2`).

## 2. Как ITkey доставляет файл клиентам

В образах `nova-compute`, `cinder-volume` и `glance-api` обеих проверенных версий
файл создаётся при сборке командой из истории образа:

```sh
echo -e "defaults {\n}" > /etc/multipath.conf
```

Фактическое содержимое:

```conf
defaults {
}
```

Цепочка доставки: **сборка образа → файл в слое образа → файл в контейнере**.

В проверенных ролях Nova/Cinder/Glance нет доставки этого файла и записи о нём
в `config_files`. Поэтому он не рендерится из inventory, а изменение конфига
демона не обновляет клиентские файлы. Этот минимальный файл не задаёт собственных
параметров; он не является копией полной политики `multipathd`.

Проверены байты и хеши всех шести файлов. Команды сборки, имена образов и слои
сохранены в локальном файле `multipath-itkey-investigation/multipath-build-evidence.json`
(в этот репозиторий не включён). SHA-256 содержимого всех шести файлов одинаков:

```text
61da9d5e12c927c5be71d52860ff16e3324283dcfde0598273eab0b5245ef2a1
```

## 3. Что предложено для форка PVS

Каждая роль самостоятельно выбирает и рендерит тот же источник для данного хоста:

| Получатель | Подготовленный файл на целевом узле |
|---|---|
| `multipathd` | `/etc/kolla/multipathd/multipath.conf` |
| `nova_compute` | `/etc/kolla/nova-compute/multipath.conf` |
| `cinder_volume` | `/etc/kolla/cinder-volume/multipath.conf` |
| `glance_api`, когда нужен Cinder FC/iSCSI store с multipath | `/etc/kolla/glance-api/multipath.conf` |

Далее существующее монтирование каталога конфигурации и новая запись
в `config_files` обеспечивают установку `/etc/multipath.conf` внутри каждого
клиентского контейнера.

Это отдельные управляемые копии из одного источника. Копировать уже готовый файл
из `/etc/kolla/multipathd/` другой ролью не требуется: запуск с тегом `nova`
или `cinder` не зависит от предыдущего запуска роли демона.

Новые bind mounts в `/etc/multipath.conf` не нужны. Если такой прямой bind
уже существует, при переходе на эту схему его необходимо убрать: один путь
не должен одновременно быть mountpoint и назначением копирования
`kolla_set_configs`.

Реализация для Nova/Cinder описана в [основной инструкции](KOLLA_MULTIPATH_NOVA_CINDER_FIX.md),
условия включения Glance — в [отдельной инструкции](GLANCE_CINDER_MULTIPATH_FIX.md).

## 4. Сравнение схем

| Аспект | Проверенная схема ITkey | Рекомендация для PVS |
|---|---|---|
| Конфиг демона | Рендер и доставка Ansible | Тот же механизм |
| Конфиг клиентов | Минимальный файл в образе | Рендер и доставка Ansible |
| Хостовый `/etc/multipath.conf` | В проверенных задачах доставки нет; состояние базовой ОС и работающего хоста не установлено | Отдельная условная доставка при наличии хостовых потребителей |
| Политика клиентов | Параметры явно не заданы в файле | Согласована с выбранным источником демона |
| Настройки конкретного хоста | Применяются к демону | Применяются ко всем включённым потребителям на этом хосте |
| Изменение общего источника | Клиентские файлы остаются прежними | Обновляются при выполнении соответствующих ролей |
| Проверка клиентского файла при `reconfigure` | Файл не заявлен в `config_files` | Участвует в штатном сравнении конфигурации |
| Где менять реализацию | Сборка клиентских образов | Задачи и JSON-шаблоны Kolla-Ansible |

Базовое исправление Nova/Cinder затрагивает четыре файла Kolla-Ansible:
`tasks/config.yml` и JSON-шаблон контейнера в каждой из двух ролей.
Glance включается отдельно, если сам подключает FC/iSCSI-тома Cinder store.
`cinder_backup` также рассматривается отдельно, если сам подключает такие тома.

## 5. Поведение при reconfigure

В предлагаемой схеме при стандартном `COPY_ALWAYS` ожидается:

- Первое добавление файла или изменение его содержимого — применение
  конфигурации и перезапуск затронутого контейнера.
- Изменение mounts, например удаление старого прямого bind, — пересоздание
  контейнера.
- Повтор без изменений — отсутствие перезапуска по причине этой правки.
- Изменение или удаление управляемого файла внутри контейнера — обнаружение
  расхождения штатной проверкой и восстановление при применении.

Изменение общего источника нужно применять к ролям всех его потребителей.
Роль `multipathd` применяет изменение через обработчик перезапуска контейнера;
бесшовный reload этой схемой не обещается.

Это вывод по исходникам и контракту `kolla_set_configs --check`, а не результат
двух последовательных запусков на стенде. Идемпотентность этой правки также
не означает `changed=0` у всего плейбука.

## 6. Что остаётся отдельными задачами

В `ks2026.2` штатный шаблон демона (`ansible/roles/multipathd/templates/multipath.conf.j2`)
содержит `uxsock_timeout 30000` и профиль `HUAWEI/XSG1` с `multibus`, `prio const`
и заданными таймаутами. В проверенном шаблоне `ks2025.2.2` этого профиля нет.
Перенос профиля — отдельное решение после проверки режима конкретной СХД.

Доставка файла сама по себе не включает клиентский multipath. Отдельно нужны
соответствующие параметры Nova, Cinder image-transfer и Glance Cinder store,
а также доступ к устройствам и управляющему демону.

Совпадение файлов не доказывает совпадение эффективной политики при разных
версиях multipath-tools и дополнительных конфигурациях. Отсутствие ошибки
о недостающем файле не доказывает устранение исходных `I/O error` и проблем detach.
Приёмка требует проверки фактического multipath-пути, attach/detach,
image-transfer и повторного `reconfigure`.

**Рекомендация для PVS сохраняется:** использовать доставку через `config_files`
для управляемого содержания и обновления конфигурации. Решение ITkey с минимальным
файлом подтверждает более узкий способ устранения его отсутствия.

Код форка и инфраструктура в рамках этого сравнения не изменены.

## 7. Что должно быть на хостах

### 7.1. Как ITkey подготавливает хосты

Подготовка распределена между образом ОС, `bootstrap-servers` и ролями Kolla:

```text
Образ ОС → bootstrap-servers → Kolla multipathd → systemd-зависимости контейнеров
```

Ниже разделены подтверждённые действия исходников и состояние, которое ещё
нужно проверить на целевой ОС. Наличие задачи не доказывает её выполнение
на конкретном узле; `enable_multipathd` по умолчанию равен `"no"`.

1. **Сборка образа ОС.** В комплекте `installer 2/project_k/` рецепт
   `services/dib/elements/ubuntu-keystack/post-install.d/51-disable-multipathd`
   явно отключает и маскирует `multipathd.service` и `multipathd.socket`.
   Это действие выполняется при подготовке **Ubuntu-образа**. В изученном
   рецепте SberLinux аналогичное действие не найдено; состояние исходного
   SberLinux-образа этим поиском не установлено.

2. **Bootstrap и общая настройка ОС.** В `installer/repo/project_k/`
   pipeline `ci/keystack/deploy.yml` вызывает
   `kolla-ansible bootstrap-servers`. Встроенная коллекция `openstack.kolla`
   подготавливает ОС и контейнерный runtime. В её `roles/packages/defaults/main.yml`
   обеих проверенных версий для Debian/Ubuntu при включённом `enable_multipathd`
   добавляется `sg3-utils-udev`. Явной установки `multipath-tools` или
   `device-mapper-multipath` в этих списках нет; пакет может уже находиться
   в базовом образе. Отдельный job `host-config` запускает
   `ci/keystack/ansible-roles/site.yml` с параметрами из
   `/etc/kolla/host_config/host-config.yml`; в проверенных ролях этой общей
   настройки ОС задач multipath не найдено.

3. **Модуль ядра.** `ansible/roles/multipathd/tasks/config-host.yml` вызывает
   роль `module-load` для `dm-multipath`. Она загружает модуль через `modprobe`
   и сохраняет его загрузку в `/etc/modules-load.d/dm-multipath.conf` на хосте.
   При `kolla_action == "config"` эти действия пропускаются.

4. **Конфиг и доступ к устройствам.** Роль формирует на хосте
   `/etc/kolla/multipathd/multipath.conf`, затем устанавливает его в контейнер
   по схеме раздела 1. Контейнер привилегированный, с доступом к хостовым
   `/dev`, `/run`, `/lib/modules` и `/sys/kernel/config`.
   Хостовый `/etc/multipath.conf` эта роль не создаёт.

5. **Systemd-зависимости контейнеров.** В `ks2026.2` роль
   `systemd-dependencies` при включённых настройках и наличии соответствующих
   units создаёт следующие зависимости:

   ```text
   kolla-multipathd-container.service:
     Wants=kolla-nova_compute-container.service

   kolla-nova_compute-container.service:
     BindsTo=kolla-multipathd-container.service
   ```

   Роль проверяет обычные unit-файлы и Quadlet, записывает drop-in в
   `/etc/systemd/system/kolla-<service>-container.service.d/systemd-dependencies.conf`
   и вызывает `daemon_reload`. Это управление связями **контейнерных units**;
   оно не отключает системный `multipathd.service`. В этом шаблоне нет
   `After=` и проверки готовности SAN-путей. Параметр
   `enable_systemd_dependencies` в `ks2026.2` по умолчанию равен `"yes"`.

Источники внутри образов Kolla-Ansible:

- `/root/.ansible/collections/ansible_collections/openstack/kolla/roles/baremetal/`
  и `roles/packages/` в той же коллекции;
- `ansible/roles/multipathd/tasks/config-host.yml`, `tasks/config.yml`,
  `defaults/main.yml`, `templates/multipathd.json.j2`;
- `ansible/roles/module-load/tasks/main.yml`;
- `ansible/roles/systemd-dependencies/{defaults/main.yml,tasks/,templates/}`
  и `ansible/group_vars/all.yml` для `ks2026.2`.

**Граница подтверждения для SberLinux:** не установлены фактический состав
базового образа, установленные udev-правила, хостовый `/etc/multipath.conf`
и состояние системных `multipathd.service/socket` на работающих узлах.
Отключение демона в Ubuntu-рецепте не подтверждает его отключение в SberLinux.

Предлагаемая ниже доставка `/etc/multipath.conf` непосредственно в ОС PVS —
дополнительная условная задача для хостовых потребителей. Она не является
копированием найденной реализации ITkey.

### 7.2. Требования к целевому хосту

Контейнеры используют ядро и блочные устройства целевого хоста. Само ядро
`multipath.conf` не читает: его читают пользовательские процессы в своём
файловом окружении. Поэтому контейнеризация демона не отменяет требования
к ядру, HBA, устройствам и udev на хосте.

| Компонент | Требование для PVS с контейнерным multipathd |
|---|---|
| Доступ к FC-СХД | Работающие HBA/драйверы, FC-подключения, zoning и mapping нужных LUN |
| Device Mapper Multipath | Поддержка `dm_multipath` в ядре; роль форка загружает модуль и создаёт `/etc/modules-load.d/dm-multipath.conf` |
| Устройства и udev | Рабочая обработка событий, корректные узлы устройств и ссылки; при подключённом multipath-томе — его карта и ожидаемые пути |
| Управляющий процесс | Один согласованно управляемый `multipathd` для этих устройств; в рассматриваемой схеме — контейнер Kolla |
| Конфиги Kolla на хосте | `/etc/kolla/multipathd/multipath.conf` и, после клиентского исправления, файлы в каталогах реально используемых сервисов |
| Хостовый `/etc/multipath.conf` | Нужен для локальных потребителей политики; контейнерная копия его не заменяет |
| Хостовые пакеты multipath | Нужны в объёме, требуемом локальными утилитами и udev-правилами выбранной ОС; пакет внутри контейнера не предоставляет исполняемый файл хостовому udev |
| Состояние WWID/bindings | Проверить фактические пути и сохранение при пересоздании контейнера и перезагрузке; это состояние узла, а не общий конфиг для всех хостов |

Отсутствие карт на узле без подключённых SAN-томов само по себе не является
ошибкой. Пакет multipath на хосте также не означает, что там должен работать
второй демон.

Три разных назначения файлов:

```text
Целевой хост:
  /etc/kolla/multipathd/multipath.conf  — подготовленный Ansible файл для контейнера
  /etc/multipath.conf                  — политика для хостовых процессов

Контейнер multipathd:
  /etc/multipath.conf                  — внутренняя копия, установленная Kolla
```

Наличие первого и третьего не означает наличия второго. В проверенных ролях PVS
и ITkey задача `multipathd/tasks/config.yml` формирует первый файл;
`multipathd.json.j2` описывает установку третьего. Отдельной доставки второго
файла в этих задачах нет.

**Когда хост нужно включать в управление конфигурацией:**

- Локальные утилиты, скрипты или мониторинг запускают `multipath`.
- Хостовые udev-правила вызывают локальную утилиту multipath. Например,
  [правила multipath-tools 0.9.4](https://raw.githubusercontent.com/opensvc/multipath-tools/0.9.4/multipath/multipath.rules.in)
  вызывают `multipath -u`. Для конкретного узла проверяются установленные правила,
  а не только этот upstream-пример.
- Загрузка ОС или необходимые ей файловые системы зависят от multipath до старта
  контейнеров. При загрузке корневой ФС с multipath-LUN конфигурация участвует
  в `initramfs`; изменение обычного файла не обновляет эту копию автоматически.
  [Объяснение Red Hat](https://access.redhat.com/solutions/56014).

Если подтверждено, что хостовых потребителей нет и загрузка ОС не зависит
от multipath, отсутствие хостового файла само по себе не доказывает неисправность.
Удалять уже существующий файл на основании этого вывода не следует: сначала
нужно установить его назначение и владельца.

## 8. Как дополнить рекомендацию для PVS

Пути `ansible/...` в этом разделе относятся к предоставленному форку
`kolla-ansible-pvs`. Ниже — предлагаемая доработка, **она не внесена в код**.
Новая переменная не является существующим параметром PVS или upstream:
одной записи в `globals.yml` без добавления задачи недостаточно.

### 8.1. Определить владельца демона и область применения

Для обычного узла, у которого загрузка ОС и необходимые хостовые файловые
системы не зависят от SAN-multipath, оставить управляющим демоном контейнер Kolla.
Хостовые инструменты могут работать с теми же устройствами и читать свой конфиг.

Системные `multipathd.service` и `multipathd.socket` не должны запускать
дополнительный демон. Их отключение/маскирование относится к подготовке ОС
после проверки зависимостей, а не к задаче доставки конфига. Уже работающий
хостовый демон нельзя автоматически останавливать при первом включении флага:
переход к контейнерному управлению требует отдельного плана применения.

Для SAN-boot или важных хостовых ФС на multipath сначала определить схему
раннего запуска, `initramfs` и последующего владения демоном. Пример ниже
не выполняет такую миграцию. При намеренном хостовом управлении потребуется
отдельно адаптировать размещение роли и клиентские условия; запуск второго
демона ради `enable_multipathd` недопустим.

Проверить inventory: в штатном `multinode` группа `multipathd` включает
`compute` и `storage`. Glance-узлы с Cinder FC/iSCSI store должны иметь нужный
SAN-доступ и выбранного управляющего демона; один тег `glance` этого не создаёт.
Не распространять multipath на все контроллеры только из-за наличия Cinder API.

### 8.2. Сохранить единый источник политики

Оставить порядок выбора из раздела 1. Существующий нужный хостовый конфиг
сначала учесть в выбранном источнике на deploy-узле, включая необходимые
исключения для локальных дисков и хостовых LUN. Пользовательский файл заменяет
шаблон целиком; `skip_kpartx yes` требует проверки нужных host-разделов.

Шаблон общей политики должен опираться на согласованные host/inventory-переменные.
Условия, зависящие от роли-получателя, могут дать разные байты даже из одного
исходника — поэтому совпадение результатов проверяется хешами.

Существующую доставку в `multipathd` сохранить. Для Nova/Cinder применить
четыре изменения из [основной инструкции](KOLLA_MULTIPATH_NOVA_CINDER_FIX.md),
для нужного Glance store — условия и изменения из
[инструкции Glance](GLANCE_CINDER_MULTIPATH_FIX.md).

### 8.3. Добавить условную доставку на сам хост

В `ansible/roles/multipathd/defaults/main.yml` добавить на верхнем уровне:

```yaml
# Предлагаемая новая переменная; включать после проверки хостовых потребителей.
multipathd_manage_host_config: false
```

В `ansible/roles/multipathd/tasks/config-host.yml`, после существующей задачи
загрузки модуля, добавить:

```yaml
- name: Render multipath.conf for host consumers
  vars:
    service: "{{ multipathd_services['multipathd'] }}"
  become: true
  template:
    src: "{{ item }}"
    dest: /etc/multipath.conf
    owner: root
    group: root
    mode: "0644"
    backup: true
  with_first_found:
    - "{{ node_custom_config }}/multipath/{{ inventory_hostname }}/multipath.conf"
    - "{{ node_custom_config }}/multipath.conf"
    - "{{ role_path }}/templates/multipath.conf.j2"
  when:
    - kolla_action != "config"
    - enable_multipathd | bool
    - multipathd_manage_host_config | bool
    - service | service_enabled_and_mapped_to_host
```

В форке `deploy.yml` уже вызывает `config-host.yml`, затем `config.yml`,
проверку контейнеров и обработчики; `reconfigure.yml` импортирует `deploy.yml`.
Новый импорт и отдельный обработчик хостового демона не нужны.

На проверенных узлах включить переменную в используемых deployment-процессом
`host_vars`/`group_vars`, либо в `globals.yml`, если настройка подходит всем
узлам роли:

```yaml
multipathd_manage_host_config: true
```

Перед включением нужно разрешить конфликт с другим владельцем файла, если он
есть: роль ОС, конфигурационный агент, symlink или mountpoint. `backup: true`
сохраняет предыдущий файл при изменении, но не делает замену работающей политики
безопасной автоматически. Параметры `template` описаны в
[документации Ansible](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/template_module.html).

При `false` задача пропускается и существующий файл сохраняется. Выключение
флага после включения не удаляет файл и не откатывает политику.

Результат для узла с включённой доставкой:

```text
Один выбранный источник на deploy-узле
  ├─ template → /etc/multipath.conf                         → хостовые утилиты/udev
  ├─ template → /etc/kolla/multipathd/multipath.conf         → контейнер демона
  ├─ template → /etc/kolla/nova-compute/multipath.conf       → nova_compute
  ├─ template → /etc/kolla/cinder-volume/multipath.conf      → cinder_volume
  └─ template → /etc/kolla/glance-api/multipath.conf         → glance_api, если нужен
```

Для контейнеров сохраняется установка через `config_files`; хостовый файл
рендерится непосредственно в `/etc/multipath.conf`. Не использовать `remote_src`
из каталога другого сервиса и не подменять этой задачей файлы WWID/bindings.
Пути и сохранение состояния multipath проверяются отдельно по используемой сборке.

### 8.4. Применять согласованно

Сначала подготовить источник и все нужные роли, затем применить на пилотном
наборе узлов в согласованное окно. Пример для существующего узла `compute03`
после подстановки реального inventory:

```bash
kolla-ansible reconfigure -i /path/to/inventory \
  --limit compute03 --tags multipathd,nova,cinder,glance
```

Указать только нужные для развёртывания теги и фактические пилотные узлы.
Для Glance/Cinder на других хостах выбрать соответствующий набор отдельно.
Ограничение `--limit` должно быть совместимо с топологией и задачами форка.

Это операция применения, способная перезапустить/пересоздать контейнеры.
Обновление host-файла, контейнерных копий и политики в памяти демона не является
одной атомарной операцией: новые хостовые вызовы могут прочитать обновлённый файл
раньше применения контейнерной части. Поэтому запуск только клиентского тега
не заменяет согласованное применение общей политики.

Не добавлять автоматические `multipath -F`, пересканирование SCSI,
`udevadm trigger`, перезагрузку или безусловный restart в эту задачу доставки.
Для SAN-boot обновление `initramfs` и проверка загрузки выполняются отдельной
процедурой для конкретной ОС; приведённый пример этого не делает.

## 9. Проверка на хостах и приёмка PVS

Следующие команды — чтение состояния на целевом Linux-узле с нужными правами.
Для Docker заменить `podman` на `docker`; имена контейнеров уточнить по списку.

```bash
hostname -f
podman ps --format '{{.Names}} {{.Image}}'
pgrep -a -x multipathd
systemctl show multipathd.service multipathd.socket \
  -p Id -p ActiveState -p SubState -p MainPID -p UnitFileState
ls -ld /sys/module/dm_multipath
ls -l /etc/modules-load.d/dm-multipath.conf
ls -l /etc/multipath.conf /etc/kolla/multipathd/multipath.conf
grep -RnsE 'multipath|kpartx' /etc/udev/rules.d /usr/lib/udev/rules.d
findmnt -no SOURCE,FSTYPE /
lsblk -o NAME,TYPE,PKNAME,WWN,MOUNTPOINTS
```

Отсутствующий unit, каталог правил или необязательный host-файл оценивать
по выбранной схеме. `pgrep` на хосте видит и контейнерные процессы: принадлежность
PID проверять по контейнеру/cgroup. Неактивный системный service при работающем
контейнере может быть нормальным. `findmnt /` — только начало проверки SAN-boot:
для LVM/dm-crypt проследить нижележащие устройства и важные хостовые mountpoints.
Наличие строки в udev-правиле ещё не доказывает её выполнение для конкретного LUN.

После подтверждения единственного управляющего демона и отсутствия неожиданной
активации системного socket проверить подготовленные файлы и контейнерные копии.
Выполнять команды только для файлов и сервисов, предусмотренных на этом узле:

```bash
sha256sum /etc/multipath.conf /etc/kolla/multipathd/multipath.conf
sha256sum /etc/kolla/nova-compute/multipath.conf
podman exec -u 0 multipathd sha256sum /etc/multipath.conf
podman exec -u 0 nova_compute sha256sum /etc/multipath.conf
podman exec -u 0 multipathd multipathd show status
podman exec -u 0 multipathd multipathd show maps topology
podman exec -u 0 multipathd multipathd show config
podman exec -u 0 nova_compute multipath -t
```

Аналогично проверить используемые `cinder_volume`, `glance_api` и `cinder_backup`.
При наличии хостового клиента отдельно прочитать его конфигурацию через
`multipath -t`. Эта команда показывает локально разобранную политику;
`multipathd show config` — политику работающего демона. Сравнить версии пакетов,
дополнительные конфиги и применимый профиль нужного устройства: одинаковые байты
основного файла не гарантируют одинаковую эффективную политику.

Общий `/run` сам по себе не доказывает доступность сокета во всех сборках.
Проверить доступ к выбранному демону из реально используемых клиентских
контейнеров и фактические namespaces. Успешный вызов от root не заменяет проверку
пути сервиса через rootwrap/privsep.

Критерии приёмки:

1. Определён владелец демона; дополнительное системное управление не запускается.
2. Установлена необходимость host-файла; при включении он управляется Ansible
   из согласованного источника, без конфликта с другим владельцем.
3. Ожидаемые файлы совпадают на одном хосте, эффективная политика проверена,
   нужный том использует multipath-карту и ожидаемые SAN-пути.
4. Attach/detach и применимые операции image-transfer проходят; отключение одного
   тестового тома не нарушает I/O другого. Проверено сохранение состояния узла.
5. Повторное применение без изменений не меняет host-файл и не перезапускает
   контейнеры из-за этого исправления. Остальные задачи плейбука оцениваются отдельно.

**Граница результата:** документ описывает проверенный по исходникам механизм
ITkey, целевую схему PVS и предлагаемую Ansible-задачу. Это не подтверждение
host-конфигурации ITkey или PVS в эксплуатации.
Код ролей, состояние сервисов, конфигурация хостов и `initramfs` не изменены;
стендовая приёмка не выполнена.
