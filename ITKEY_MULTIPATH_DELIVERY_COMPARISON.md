# Доставка multipath.conf: ITkey и рекомендации для форка PVS

Дата проверки: **14.10.2026**.

Основа: локальные образы ITkey `ks2025.2.2` и `ks2026.2`, извлечённые роли
Kolla-Ansible и ранее подготовленные рекомендации для `kolla-ansible-pvs`.
Проверены исходники и содержимое архивов. Работающая инфраструктура не проверялась.

Пути `ansible/...` ниже относятся к каталогу
`/var/lib/kolla/venv/share/kolla-ansible/` внутри образа
`repo.itkey.com/project_k/kolla-ansible:ks2026.2`.
Клиентские образы имеют имена `repo.itkey.com/project_k/<service>:<release>-sberlinux`,
где `<service>` — `nova-compute`, `cinder-volume` или `glance-api`,
а `<release>` — `ks2025.2.2` или `ks2026.2`.
Они исследованы в архивах `keystack-ks2025.2.2-sberlinux-docker-images.tar`
и `keystack-ks2026.2-sberlinux-docker-images.tar` из локального комплекта ITkey.
Архивы и извлечённые исходники в этот документационный репозиторий не включены.

## Краткий вывод

У ITkey используются два способа доставки:

- **`multipathd`:** полноценный конфиг рендерится Ansible и устанавливается
  в контейнер через `config_files` и `kolla_set_configs`.
- **Nova/Cinder/Glance:** минимальный `/etc/multipath.conf` заранее создаётся
  при сборке образов; соответствующие роли не рендерят и не доставляют этот файл.

Рекомендация для форка PVS расширяет штатный механизм Ansible на клиентские
контейнеры: каждый получает управляемую копию конфигурации из того же источника,
который выбран для демона на данном хосте.

Минимальный файл ITkey закрывает отсутствие `/etc/multipath.conf`. Предлагаемая
схема дополнительно обеспечивает управление содержимым и его обновлениями.
Полный одинаковый файл нельзя объявлять обязательным условием любого работающего
multipath-развёртывания.

## 1. Как ITkey доставляет конфиг демона

Роль `multipathd` выбирает первый существующий источник:

```text
1. {{ node_custom_config }}/multipath/{{ inventory_hostname }}/multipath.conf
2. {{ node_custom_config }}/multipath.conf
3. roles/multipathd/templates/multipath.conf.j2
```

При стандартных путях первые два источника находятся на узле развёртывания
в `/etc/kolla/config/`. В host-specific пути используется имя из inventory.

```text
Узел развёртывания:
выбранный источник
    │ Ansible template: Jinja-рендер для целевого хоста
    ▼
Целевой узел:
/etc/kolla/multipathd/multipath.conf
    │ каталог /etc/kolla/multipathd/ смонтирован в контейнер read-only
    ▼
Контейнер multipathd:
/var/lib/kolla/config_files/multipath.conf
    │ kolla_set_configs: установка по описанию в config.json
    ▼
/etc/multipath.conf
    │
    ▼
чтение демоном multipathd
```

Ansible отдельно рендерит `multipathd.json.j2` в
`/etc/kolla/multipathd/config.json`. В нём объявлены источник, назначение,
владелец и права файла. В контейнере Jinja-рендера этого конфига уже нет:
`kolla_set_configs` устанавливает подготовленный файл.

**`with_first_found` не объединяет конфиги.** Пользовательский файл целиком
заменяет штатный шаблон. Huawei-профиль из шаблона `ks2026.2` автоматически
к пользовательскому конфигу не добавляется.

Источники: задачи роли (`ansible/roles/multipathd/tasks/config.yml`),
монтирования (`ansible/roles/multipathd/defaults/main.yml`),
JSON-шаблон (`ansible/roles/multipathd/templates/multipathd.json.j2`).

## 2. Как ITkey доставляет файл клиентам

В образах `nova-compute`, `cinder-volume` и `glance-api` обеих проверенных версий
файл создаётся при сборке командой из истории образа:

```sh
echo -e "defaults {\n}" > /etc/multipath.conf
```

Фактическое содержимое:

```conf
defaults {
}
```

Цепочка доставки: **сборка образа → файл в слое образа → файл в контейнере**.

В проверенных ролях Nova/Cinder/Glance нет доставки этого файла и записи о нём
в `config_files`. Поэтому он не рендерится из inventory, а изменение конфига
демона не обновляет клиентские файлы. Этот минимальный файл не задаёт собственных
параметров; он не является копией полной политики `multipathd`.

Проверены байты и хеши всех шести файлов. Команды сборки, имена образов и слои
сохранены в локальном файле `multipath-itkey-investigation/multipath-build-evidence.json`
(в этот репозиторий не включён). SHA-256 содержимого всех шести файлов одинаков:

```text
61da9d5e12c927c5be71d52860ff16e3324283dcfde0598273eab0b5245ef2a1
```

## 3. Что предложено для форка PVS

Каждая роль самостоятельно выбирает и рендерит тот же источник для данного хоста:

| Получатель | Подготовленный файл на целевом узле |
|---|---|
| `multipathd` | `/etc/kolla/multipathd/multipath.conf` |
| `nova_compute` | `/etc/kolla/nova-compute/multipath.conf` |
| `cinder_volume` | `/etc/kolla/cinder-volume/multipath.conf` |
| `glance_api`, когда нужен Cinder FC/iSCSI store с multipath | `/etc/kolla/glance-api/multipath.conf` |

Далее существующее монтирование каталога конфигурации и новая запись
в `config_files` обеспечивают установку `/etc/multipath.conf` внутри каждого
клиентского контейнера.

Это отдельные управляемые копии из одного источника. Копировать уже готовый файл
из `/etc/kolla/multipathd/` другой ролью не требуется: запуск с тегом `nova`
или `cinder` не зависит от предыдущего запуска роли демона.

Новые bind mounts в `/etc/multipath.conf` не нужны. Если такой прямой bind
уже существует, при переходе на эту схему его необходимо убрать: один путь
не должен одновременно быть mountpoint и назначением копирования
`kolla_set_configs`.

Реализация для Nova/Cinder описана в [основной инструкции](KOLLA_MULTIPATH_NOVA_CINDER_FIX.md),
условия включения Glance — в [отдельной инструкции](GLANCE_CINDER_MULTIPATH_FIX.md).

## 4. Сравнение схем

| Аспект | Проверенная схема ITkey | Рекомендация для PVS |
|---|---|---|
| Конфиг демона | Рендер и доставка Ansible | Тот же механизм |
| Конфиг клиентов | Минимальный файл в образе | Рендер и доставка Ansible |
| Политика клиентов | Параметры явно не заданы в файле | Согласована с выбранным источником демона |
| Настройки конкретного хоста | Применяются к демону | Применяются ко всем включённым потребителям на этом хосте |
| Изменение общего источника | Клиентские файлы остаются прежними | Обновляются при выполнении соответствующих ролей |
| Проверка клиентского файла при `reconfigure` | Файл не заявлен в `config_files` | Участвует в штатном сравнении конфигурации |
| Где менять реализацию | Сборка клиентских образов | Задачи и JSON-шаблоны Kolla-Ansible |

Базовое исправление Nova/Cinder затрагивает четыре файла Kolla-Ansible:
`tasks/config.yml` и JSON-шаблон контейнера в каждой из двух ролей.
Glance включается отдельно, если сам подключает FC/iSCSI-тома Cinder store.
`cinder_backup` также рассматривается отдельно, если сам подключает такие тома.

## 5. Поведение при reconfigure

В предлагаемой схеме при стандартном `COPY_ALWAYS` ожидается:

- Первое добавление файла или изменение его содержимого — применение
  конфигурации и перезапуск затронутого контейнера.
- Изменение mounts, например удаление старого прямого bind, — пересоздание
  контейнера.
- Повтор без изменений — отсутствие перезапуска по причине этой правки.
- Изменение или удаление управляемого файла внутри контейнера — обнаружение
  расхождения штатной проверкой и восстановление при применении.

Изменение общего источника нужно применять к ролям всех его потребителей.
Роль `multipathd` применяет изменение через обработчик перезапуска контейнера;
бесшовный reload этой схемой не обещается.

Это вывод по исходникам и контракту `kolla_set_configs --check`, а не результат
двух последовательных запусков на стенде. Идемпотентность этой правки также
не означает `changed=0` у всего плейбука.

## 6. Что остаётся отдельными задачами

В `ks2026.2` штатный шаблон демона (`ansible/roles/multipathd/templates/multipath.conf.j2`)
содержит `uxsock_timeout 30000` и профиль `HUAWEI/XSG1` с `multibus`, `prio const`
и заданными таймаутами. В проверенном шаблоне `ks2025.2.2` этого профиля нет.
Перенос профиля — отдельное решение после проверки режима конкретной СХД.

Доставка файла сама по себе не включает клиентский multipath. Отдельно нужны
соответствующие параметры Nova, Cinder image-transfer и Glance Cinder store,
а также доступ к устройствам и управляющему демону.

Совпадение файлов не доказывает совпадение эффективной политики при разных
версиях multipath-tools и дополнительных конфигурациях. Отсутствие ошибки
о недостающем файле не доказывает устранение исходных `I/O error` и проблем detach.
Приёмка требует проверки фактического multipath-пути, attach/detach,
image-transfer и повторного `reconfigure`.

**Рекомендация для PVS сохраняется:** использовать доставку через `config_files`
для управляемого содержания и обновления конфигурации. Решение ITkey с минимальным
файлом подтверждает более узкий способ устранения его отсутствия.

Код форка и инфраструктура в рамках этого сравнения не изменены.
